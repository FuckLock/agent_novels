# code-reviewer Agent 逐节深度讲解（学生版）

> 这不是实施计划，是教学讲义。目的：帮你彻底看懂 Agent 每一节的优缺点、是否需要、位置对不对、怎么改。
>
> 配套阅读：`code-review-skill-讲义.md`（讲 Skill 文件怎么写），本篇讲 **Agent 文件怎么写**。两者分工不同。

---

## 先铺垫一下：Agent 和 Skill 到底是啥关系？

这是**最常被搞混**的地方。一句话拆清楚：


|        | Skill               | Agent                          |
| ------ | ------------------- | ------------------------------ |
| 本质     | **工作说明书**（怎么干活的手册）  | **一个人**（拿着说明书的员工）              |
| 管什么    | 规则、流程、输出格式、维度清单     | 身份、性格、和谁说话、用哪本手册               |
| 能独立存在吗 | 可以被主 Agent 直接调用     | **必须**携带至少一个 Skill 才有用         |
| 关键字段   | [任务]、[第一性原则]、[工作流程] | `skills:`、`model:`、[角色]、[协作模式] |


### 类比：餐厅

- **Skill** = 菜谱（"红烧肉怎么做"——选料、下锅顺序、火候）
- **Agent** = 厨师（"老王，上岗 20 年，脾气暴，不炒素菜，只按菜谱走"）
- **主 Agent（大东）** = 餐厅老板（决定今天派老王还是小李做哪道菜）

### 为什么要分家？

你可能会问："既然 Skill 已经讲清楚怎么审代码了，为什么还要一个 Agent 文件？直接让主 Agent 调 Skill 不就完了？"

**三个理由**：

1. **上下文隔离**：主 Agent 积累了一堆和用户聊产品需求的对话历史。这些历史对审代码**没用还有害**（可能污染判断）。新开一个 sub-agent，它是"白纸一张"进来干活。
2. **角色扮演**：Skill 是中立的工作手册。Agent 是带人设的执行者。"你是严格的 QA，不信任声明" 这种话是 Agent 说的，不是 Skill 说的。
3. **模型选择**：Agent 可以指定 `model: opus`——不同任务用不同档位的模型。审代码要仔细，用大模型；执行机械任务用小模型，省钱。

**记住这三点，后面读每一节都会清楚。**

## code-reviewer.md 在干啥？

当前这个文件一共 43 行，5 个结构块：

```
1. Frontmatter        - 系统识别用
2. [角色]              - 谁在审？性格是啥？
3. [任务]              - 审什么？审几步？
4. [输出规范]          - 审完怎么说？
5. [协作模式]          - 和谁对接？什么节奏？
```

对比一下 Skill 通常有 7-10 节。**Agent 比 Skill 短，是正常的**——它是薄壳，主要内容在 Skill 里。

## 每节讲解的固定格式（老六问）

对每一节，我都问这 6 个问题：

1. **它在说啥**（大白话）
2. **好在哪**
3. **差在哪**
4. **咋改 + 为啥改**
5. **要不要**（保留/删除）
6. **位置对不对**（该排第几）

## 节 1：Frontmatter

```yaml
---
name: code-reviewer
description: 当需要代码审查时由主 Agent 派发。使用 code-review skill 对照 Spec 和设计稿审查代码，输出结构化报告返回给主 Agent。
skills: code-review
model: opus
color: red
---
```

### 在说啥

Agent 的身份证。比 Skill 的 Frontmatter **多两个关键字段**：

- `skills: code-review` — 这个 Agent 要用哪本手册
- `model: opus` — 用哪档模型
- `color: red` — 在 UI 里显示什么颜色（提示用户"这是严肃的审查任务"）

### 好在哪

- `**skills` 字段明确**：一看就知道这个 Agent 的"工作手册"是哪本。不装 Skill 就是废人。
- `**model: opus` 选得对**：审代码需要细致推理，小模型容易漏。这一行决定了审查质量的下限。
- `**description` 写的是"触发时机 + 职责"**：不是"我能干啥"（像简历），而是"什么场景叫我来"（像调度手册）——这种写法**让主 Agent 更容易决定派不派**。
- `**color: red`** 提示用户这是严格检查类任务。视觉上和"绿色=开发"、"黄色=审查"有区分。

### 差在哪

- **没写 `tools`**：没限制 Agent 能用什么工具。审查是**只读任务**（Read、Grep、Glob、Bash 跑测试），它**不应该能 Edit / Write**。但当前 Frontmatter 没限制，理论上它可以偷偷改代码。
- `**skills` 只绑了一个**：但审查其实可能用到 `bug-fixer` skill 吗？不，职责清楚就一个——这点其实是**对的**。但如果未来扩展（比如加安全深度扫描 skill），得能挂多个。
- **没版本号**：Agent 改了之后没法追溯。
- `**description` 省略了"不干啥"**：只说"审查 + 返回报告"，没明文说"不修代码"。虽然 [协作模式] 里提了，但 Frontmatter 是自动路由时最先被读的地方，应该也挡一下。

### 咋改 + 为啥改

```yaml
---
name: code-reviewer
description: 当需要代码审查时由主 Agent 派发。使用 code-review skill 对照 Spec 和设计稿审查代码，输出结构化报告返回给主 Agent。不执行任何修改。
skills: [code-review]
model: opus
color: red
tools: [Read, Grep, Glob, Bash]
version: 1.0
---
```

四处改动：

1. **description 末尾加"不执行任何修改"**：让路由层就挡掉越界意图。
2. `**skills` 改成数组**：未来能扩展（即便现在只挂一个）。
3. **新增 `tools` 白名单**：审查是只读，**物理上**阻断写操作。这比"[协作模式] 写一句'不修代码'"硬 100 倍——Agent 想修也没这个工具。
4. **加 `version`**：未来能追溯。

- **为啥限制工具是最关键改动**：
你告诉 AI"别改代码"，它大部分时候会听。但**偶尔**它会"好心帮忙"——"我发现一个明显的 bug，顺手改了"。这是 Sub-Agent 越权的典型故障模式。**用工具白名单物理切断，比用文字提醒管用**。

### 要不要

**必须要**。

### 位置对不对

**第 1，对的**。✅（系统要求）

## 节 2：[角色]

```
[角色]
    你是一名严格的 QA 工程师，专门对照需求文档和设计稿审查代码实现。

    你不信任任何"应该没问题"的声明——每个结论必须有证据。
    你不接受"大致匹配"——要么匹配要么不匹配。
    你不跳过任何 Spec 条目——每一条都必须被检查到。
```

### 在说啥

给 Agent **装人设**。三句"不 X"是核心——把它变成一个**挑刺型人格**。

### 好在哪

- **人设和 Skill 的第一性原则对齐**：Skill 里有"不信任声明 / 证据为王 / 不放过"，Agent 这里用人设语气重复了一遍。**这不是冗余，是强化**。
- **三句话节奏整齐**：都是"不 X——Y"格式。AI 读到这种排比会**把它当作强约束**。
- **"严格的 QA 工程师" 这个身份选得好**：QA 天生的工作就是挑错，不是鼓励。AI 代入这个角色后，不会倾向"夸一夸代码"。

### 差在哪

- **人设和 Skill 原则耦合太紧**：Skill 改了原则，Agent 忘了跟着改——两处会飘。典型的 DRY 违规。
- **缺"不做什么"的边界**：人设只讲了"审查时的态度"，没讲"**边界之外是什么**"。比如：
  - 能不能直接和用户对话？（[协作模式] 说不能，但[角色] 没提）
  - 发现 bug 能不能顺手改？（没明文说，人设给了"严格"但没给"只审不修"）
- **"严格 QA" 有个副作用**：过度严格 = 误报率高。没有"务实"这层 buffer，AI 可能把一些正常的权衡（比如 `any` 类型在某些场景合理）也标为问题。

### 咋改 + 为啥改

```
[角色]
    你是一名严格但务实的 QA 工程师，专门对照需求文档和设计稿审查代码实现。

    核心人格（铁律，与 code-review skill 第一性原则对齐）：
    - 你不信任任何"应该没问题"的声明——每个结论必须有证据
    - 你不接受"大致匹配"——要么匹配要么不匹配
    - 你不跳过任何 Spec 条目——每一条都必须被检查到

    边界（不可逾越）：
    - 你只审查，不修改：发现问题只记录，不调用 Edit/Write
    - 你只对主 Agent 汇报，不直接和用户交流
    - 你不做超出 Skill 定义的审查维度（保持可预测）

    务实性 buffer：
    - 当 Spec 条目明显可解释为多种理解时，标 ❓ 而非 ❌
    - 当代码做了 Spec 未要求的合理工程优化时，标 💡 而非 ❌
```

四处改动：

1. **"严格" → "严格但务实"**：避免过度挑刺。
2. **核心人格加注释** "与 code-review skill 第一性原则对齐"：明确这是镜像关系，修改时要同步。
3. **新增"边界"区块**：明文写死"不修改、不直接对话、不扩展维度"。这三条是 Sub-Agent **最容易越权**的地方。
4. **新增"务实性 buffer"**：给 AI 一个"合理妥协"的路径，防止过度挑刺变成制造噪音。

- **为啥要"务实性 buffer"**：  
没 buffer 的严格 QA 会把"代码用了 `any` 类型"、"函数名用了英文而非驼峰"、"import 顺序不规范"这些鸡毛蒜皮都写进报告——**报告一长，重点就被稀释**。给 AI 一条"可以标为💡而非❌"的路径，它就知道哪些是"值得提但非阻塞"的。

### 要不要

**必须要**。人设是 Agent 区别于 Skill 的核心。

### 位置对不对

**第 2 位，对的**。✅  
Agent 里人设要尽早出现——它决定了后面所有行为的基调。

## 节 3：[任务]

```
[任务]
    收到主 Agent 派发后，使用 code-review skill 执行两阶段代码审查：

    Stage 1 — Spec Compliance（做对了没有？）：
    - 功能完整性审查（Spec 逐条 vs 代码）
    - UI 一致性审查（设计稿 vs 实际页面，如有）
    - Spec 漂移检测（代码中有无 Spec 没写的功能）

    Stage 1 通过后进入 Stage 2 — Code Quality（做好了没有？）：
    - 代码质量审查（命名、类型、结构、文件大小）
    - 安全扫描（密钥、注入、危险函数）

    Stage 1 有 HIGH priority 问题时，停在 Stage 1，不执行 Stage 2。
```

### 在说啥

"你这次来干什么活"。两阶段流程 + 门槛规则。

### 好在哪

- **两阶段分层好**：和 Skill 里的 Stage 1/Stage 2 **保持一致**——Agent 和 Skill 用同一语言。
- **每个 Stage 列出 2-3 个具体维度**：不是空谈，AI 知道具体查什么。
- **明文写了门槛**："Stage 1 有 HIGH → 停"，给了流程控制逻辑。

### 差在哪（**最大问题**：和 Skill 严重重复）

这节最大的毛病是——**几乎整段内容都在 Skill 里已经定义过了**。


| 这节内容              | Skill 的对应位置              | 关系  |
| ----------------- | ------------------------ | --- |
| 功能完整性审查           | code-review skill [审查维度] | 重复  |
| UI 一致性审查          | code-review skill [审查维度] | 重复  |
| Spec 漂移检测         | code-review skill [审查维度] | 重复  |
| 代码质量审查            | code-review skill [审查维度] | 重复  |
| 安全扫描              | code-review skill [审查维度] | 重复  |
| Stage 门槛 "HIGH 停" | code-review skill [审查策略] | 重复  |


**等于把 Skill 的内容摘抄了一遍**。这违反了 **DRY 原则**——同一个规则只能存在一处。

**后果**：

- Skill 更新了（比如加了"性能审查"维度）→ Agent 这里没跟着改 → 两处不一致 → AI 不知道听哪个
- Skill 把"HIGH 停"改成"MEDIUM 停" → Agent 这里写的还是 HIGH → Agent 用旧规则

**另一个问题**：**HIGH 在这里和 Skill 里都没定义是什么**。Skill 讲义已经指出这是 prompt bug，Agent 里又犯了一遍。

### 咋改 + 为啥改

```
[任务]
    收到主 Agent 派发后，使用 code-review skill 执行两阶段代码审查。

    具体流程、维度、门槛规则 → 以 code-review skill 定义为准，不在本文重复定义。

    你在本次任务中的具体操作：
    1. 接收主 Agent 的审查范围（全量 / 指定 Phase / 指定 Task 的文件列表）
    2. 调用 code-review skill 按其内部流程执行
    3. 按 [输出规范] 返回结构化报告给主 Agent

    完成标准：
    - Skill 返回"两阶段通过" → 返回完整报告
    - Skill 返回"Stage 1 阻塞" → 返回仅含 Stage 1 的报告，明确标注"未进入 Stage 2"
```

四处改动：

1. **删掉所有维度清单和门槛定义**：交还给 Skill。
2. **改成"接收-调用-返回" 三步流程**：Agent 负责的是**任务接口**，不是审查细节。
3. **明确入参**：审查范围从主 Agent 接收。
4. **明确完成标准**：什么时候报告算写完。

- **为啥必须这么改**：  
**Agent 和 Skill 的分工**决定了这种拆法——
  - Skill 讲"怎么审"（审查维度、门槛、输出格式）
  - Agent 讲"任务接口"（接收什么、返回什么、边界条件）
  把"怎么审"写进 Agent = 越级 = DRY 违规 = 未来必飘。

### 要不要

**必须要**（改写后）。

### 位置对不对

**第 3 位，对的**。✅  
任务说明紧跟人设是合理的——先知道你是谁，再知道你要干什么。

## 节 4：[输出规范]

```
[输出规范]
    - 中文
    - 结构化报告（按 code-review skill 定义的格式输出）
    - 每项结论附文件路径:行号
    - 编译结果附原始输出
```

### 在说啥

"审完怎么说"。四条输出要求。

### 好在哪

- **第二条"按 skill 定义的格式"是好设计**：不重复定义格式，引用 Skill。这和节 3 的大毛病相反——这里做对了。
- **"中文"、"附行号"、"附原始输出" 都是硬约束**，AI 不能含糊。
- **很简洁**：4 条，不啰嗦。Agent 的输出规范本就不该长。

### 差在哪

- **"结构化报告（按 code-review skill 定义的格式输出）" 不够具体**：Agent 不知道 Skill 里定义的格式"长啥样"。如果 Skill 的输出格式有多种（比如全量审查 vs 单 Task 审查），Agent 不知道选哪种。
- **没有"返回给谁"的约束**：输出规范只讲了"输出啥"，没讲"输出给谁"。Agent 可能误以为是输出给用户（像主 Agent 一样直接对话），但实际上它是**返回给主 Agent**的内部结果。
- **没有长度/密度要求**：编译输出原始贴过来可能上千行，没限制就会污染主 Agent 的上下文。
- **没有异常格式**：如果 Skill 失败（比如依赖检测没过），Agent 怎么汇报？没说。

### 咋改 + 为啥改

```
[输出规范]
    输出对象：主 Agent（不是用户）。格式要机器可解析，同时人类可读。

    基本要求：
    - 中文
    - 结构化报告，格式见 code-review skill [输出格式]节
    - 每项结论附"文件路径:行号"
    - 编译/测试输出：只附失败部分（最多 50 行），成功时只写一句"✓ 通过"

    状态字段（必填，放在报告开头，供主 Agent 路由用）：
      status: passed | stage1_blocked | stage2_blocked | skill_failed
      stage_reached: 1 | 2
      failure_count: { critical: N, high: N, medium: N, low: N }

    异常处理：
    - Skill 依赖检测失败 → status: skill_failed，附失败原因
    - 审查过程中工具报错 → 中止并返回 status: skill_failed
```

四处改动：

1. **明确输出对象**：告诉 Agent 你是在汇报给机器上游，不是给人类讲话。风格要服从这个目的。
2. **引用 Skill 输出格式时给具体节名**：`code-review skill [输出格式]节` 比"按 skill 定义的格式"精确 10 倍。
3. **限制编译输出长度**：防止原始日志污染上下文。
4. **新增 `status` 字段**：主 Agent 需要一个**机器可读的路由线索**，不用解析整段报告就能知道"过没过"。

- **为啥 status 字段是救命的**：  
主 Agent 收到报告后要做决策："是进 fix 循环，还是让用户确认？"  
如果只有 Markdown 报告，主 Agent 得**阅读理解**整份报告才能判断——慢、贵、易错。  
有 `status: stage1_blocked` 这一行，主 Agent **直接分支**即可——快、稳、便宜。

### 要不要

**必须要**（扩充后）。

### 位置对不对

**第 4 位，可接受但不是最优**。  
建议和 [协作模式] 互换——先讲"和谁对接、什么节奏"，再讲"输出什么"。**因为输出是"给谁"的函数——不知道给谁，谈输出规范没意义**。

## 节 5：[协作模式]

```
[协作模式]
    你是主 Agent 调度的 Sub-Agent：
    1. 收到主 Agent 派发指令和审查材料
    2. 使用 code-review skill 执行两阶段审查
    3. 输出结构化报告返回给主 Agent。报告可能只包含 Stage 1（如果 Stage 1 未通过），也可能包含两个 Stage
    4. 主 Agent 根据失败的 Stage 决定修复路径

    你不直接和用户交流，不执行修复，只做审查和报告。
```

### 在说啥

"你的位置、你的上游、你的边界"。四步协作流程 + 三条边界。

### 好在哪

- **"你是 Sub-Agent" 这句开宗明义**：很多 Agent 忘了讲自己的位置，结果越权对话。
- **边界明文写死**："不直接和用户交流，不执行修复，只做审查和报告"——三条铁边界。
- **四步流程线性清晰**：收到 → 执行 → 返回 → 主 Agent 决策。

### 差在哪

- **"审查材料"没定义**：主 Agent 派发时传什么？Spec 路径？代码范围？设计稿？没明确 = 主 Agent 随便传 = Agent 做不稳。
- **和 [任务] 节重复**：第 2 步 "使用 code-review skill 执行两阶段审查" 和 [任务] 里讲的重复。
- **"不继承 session 历史" 没写**：按 CLAUDE.md 的 Sub-Agent 隔离原则，Agent 不应该假设自己知道主 Agent 之前干过什么。但这里没写明。
- **"失败后谁决策" 写得太简**：只说"主 Agent 决定修复路径"，没说 Agent 自己该不该建议修复路径。按照职责分工，**Agent 不决策但可以提线索**。

### 咋改 + 为啥改

```
[协作模式]
    你是 Sub-Agent，由主 Agent（大东）调度。你不继承主 Agent 的 session 历史。

    派发接口（主 Agent 必须传给你的内容）：
    - spec_path: Product-Spec.md 路径
    - design_brief_path: Design-Brief.md 路径（可选）
    - review_scope: { mode: "full" | "phase" | "task", targets: [...] }
    - code_root: 项目代码根目录
    - design_files: 设计稿文件列表（可选）

    若主 Agent 漏传关键字段 → status: skill_failed，明确列出缺失项，不要自己猜。

    工作流程：
    1. 验证派发接口完整性
    2. 调用 code-review skill，将上述参数传入
    3. 按 [输出规范] 组装报告
    4. 返回给主 Agent（不直接输出给用户）

    边界（铁律）：
    - 不直接和用户交流
    - 不调用 Edit/Write 修复问题（Frontmatter 已限制）
    - 不继承之前 Task 的假设——每次都当作全新任务
    - 不决策修复路径（这是主 Agent 的职责）

    协作提示（非决策）：
    - 报告末尾可附"建议"区块：哪些问题适合 /bug-fixer、哪些适合调整 Spec
    - 这是参考信息，主 Agent 可采纳可忽略
```

五处改动：

1. **明确"不继承 session 历史"**：CLAUDE.md 里的隔离原则要在 Agent 自身明文强化一遍。
2. **列出派发接口**：主 Agent 必须传啥写死。传少了 Agent 要**明确拒绝**，不要自己猜。
3. **"验证派发接口完整性" 变第 1 步**：Fail Fast 原则。
4. **把三条边界变成铁律块**：比散在文字里强 10 倍。
5. **新增"协作提示（非决策）" 区块**：Agent 可以给修复建议，但明确这是参考，不是决策。

- **为啥接口要明文写**：  
主 Agent 调用 Sub-Agent 就像函数调用——**参数不明会挂掉**。现在的写法相当于"传一个 dict 过来，字段随意"，典型的野接口。**列出必填字段 + 失败时明确拒绝**，让 Agent 之间的协作像 API 一样可预测。
- **为啥新增"协作提示"**：  
Agent 不决策，但 Agent 有信息优势——它刚审完代码，对哪些问题"好修"最有发言权。完全不让它说 = 信息浪费。但让它决策 = 越权。  
**折中：允许提建议，明确是"参考"**。这是典型的"上下级分工最优解"——下级不僭越，但也不藏拙。

### 要不要

**必须要**（扩充后）。

### 位置对不对

**建议前移到第 4**（和 [输出规范] 互换）。  
理由见节 4 分析——先讲"和谁对接"，再讲"输出啥"。

# 🧠 理论篇：Agent 这个抽象为啥存在？

前面讲了"怎么改"。理论篇讲**"为啥 Agent 必须是 Agent，不能是 Skill"**。

---

## 理论 A：为什么不直接让主 Agent 调 Skill？

### 类比 1：餐厅老板不亲自炒菜

小餐馆 = 老板 + 菜谱 → 老板亲自炒。
大餐厅 = 老板 + 菜谱 + 厨师 → 老板只管调度，厨师按菜谱干活。

**为什么大餐厅需要厨师这一层？**

三个硬需求：

1. **专注力分配**：老板要同时对接客人、上货、营销。如果还要亲自炒菜，每道菜都不专心。分工后老板不被炒菜中断，厨师也不被客人打扰。
2. **责任边界**：客人投诉菜难吃，老板能追问厨师"你按菜谱做的吗"。没有厨师这层，责任糊在一起。
3. **可替换性**：这个厨师脾气不好？换一个性格的。不用重写菜谱。

**AI 同理**。

- 主 Agent = 老板（和用户对话，派发任务）
- Skill = 菜谱（标准化流程）
- Sub-Agent = 厨师（按菜谱干，有自己人设，对老板汇报）

### 类比 2：单线程程序 vs 多进程

**单线程**（主 Agent 直接跑 Skill）：

```
主 Agent 上下文：
├── 和用户聊的 50 轮对话
├── 项目需求讨论
├── 设计风格争辩
├── 代码审查工作区（和上面这些挤在一起）
└── 审查结论
```

问题：审查时被前面 50 轮对话**干扰**。AI 读着 Spec 审代码，一转头看到"用户之前说设计可以模糊点"——可能就把审查标准降低了。

**多进程**（派发 Sub-Agent 审查）：

```
主 Agent 上下文：     Sub-Agent 上下文：
├── 50 轮对话          ├── 任务参数
├── 需求              ├── Spec 内容
├── 设计              ├── 代码内容
└── （等待结果）       └── 审查过程
```

Sub-Agent **白纸一张进来**，只带任务需要的信息。审查结论不被污染。

**这就是隔离原则的价值**——进程隔离保证代码互不干扰，Sub-Agent 隔离保证判断互不污染。

### 为什么不直接让主 Agent "装模作样"地审？

你可能会说："主 Agent 也可以装 QA 人设，为什么非要 Sub-Agent？"

**能装，但装不干净**。AI 切换人设时**残留上一个人设的倾向**。

- 主 Agent 原本是"友好协调者"（对用户温和、主动给方案、嘲讽用户时才尖锐）
- 突然切换成"严格 QA"（不信任、不放过、不妥协）
- 结果：半温和半严格 → 审查不彻底 + 用户感觉突然变脸

**Sub-Agent 是从零开始扮演 QA**，没历史包袱。人设更纯粹。

---

## 理论 B：Agent 和 Skill 的分工边界在哪？

### 一个判断公式

**遇到一条规则，纠结放 Agent 还是 Skill？**  
问自己：

> "如果换一个不同性格的 Agent 来跑这个 Skill，这条规则应不应该跟着变？"

- **该变** → 放 Agent
- **不该变** → 放 Skill

### 举例判断


| 规则             | 换个 Agent 该变吗？         | 结论                          |
| -------------- | --------------------- | --------------------------- |
| 颜色偏差容忍度 `±0`   | 不变（任何审查员都应守此标准）       | → Skill                     |
| "严格但务实的 QA" 人设 | 变（换个温和审查员呢？）          | → Agent                     |
| 两阶段审查流程        | 不变（流程是规则，不是人格）        | → Skill                     |
| 报告用中文          | 变（国际团队可能要英文）          | → Agent                     |
| 每条结论附行号        | 不变（这是证据为王的落地）         | → Skill                     |
| 不继承 session 历史 | 不变（所有 Sub-Agent 都该如此） | → Agent（但这是 Agent **通用规范**） |
| 模型选 `opus`     | 变（轻量审查可能用 haiku 省钱）   | → Agent（Frontmatter）        |


### 当前 code-reviewer.md 的分工失误

回头看：

- **[任务] 节摘抄了 Skill 的两阶段和维度** → 分工错误（这些"换个 Agent 不该变"）
- **[协作模式] 没写派发接口** → 分工遗漏（这是"换个 Agent 也差不多"的 Agent 通用约定）

**改后的版本遵守了这条公式**：

- 流程细节交给 Skill
- 人设、接口、边界留在 Agent

## 理论 C：为什么 Sub-Agent 的"物理工具限制"比"文字约束"更重要？

### AI 的"好心越权"故障模式

场景：

1. 主 Agent 派 code-reviewer 审代码
2. code-reviewer 读代码时发现一个明显的 null pointer bug
3. 人类心理："这不就改一行就行吗，顺手改了吧"
4. AI 也有这种"讨好本能"——**想帮忙**

**如果只用文字约束**（"你不执行修复"）：

- 大多数时候 AI 会遵守
- **偶尔**（10% 概率）会越权改一下
- 主 Agent 返回时一脸懵："我没让你改啊？"

**如果用 Frontmatter `tools` 限制**（不给 Edit/Write）：

- AI **想**越权
- 调用 Edit 时工具不存在 → 报错 → 放弃
- **100% 不会越权**

### 为什么文字约束不够硬？

LLM 本质是**概率生成器**。任何文字约束都是"降低违反概率"，不是"禁止违反"。

- "你不能改代码" → 违反概率 10%
- "你绝对不能改代码" → 违反概率 8%
- "你不能改代码，违反会导致严重后果" → 违反概率 6%
- 加字数、加警告、加感叹号 → **边际效益递减，永远不是 0**

工具白名单是**另一个层级**：

- 不给 Edit → 违反概率 **0%**（物理上不可能）

### 推广：什么时候该用物理约束？


| 约束类型          | 用什么实现                 | 违反概率  |
| ------------- | --------------------- | ----- |
| "不要做 X"       | 文字提醒                  | 5-15% |
| "只能做 A 不能做 B" | 文字 + 反例               | 2-8%  |
| "绝对不能做 X"     | 工具白名单 / permission 拒绝 | 0%    |


**原则**：

- 越权后果严重（删文件、污染代码、发消息）→ 物理约束
- 越权后果轻微（多说一句废话）→ 文字约束

**code-reviewer 的越权后果**：改错代码 / 把审查变成修复。**严重**。**必须物理约束**。

## 理论 D：派发接口为啥要写死？

### 软件工程里的"函数签名"

你写一个 Python 函数：

```python
def review_code(spec_path, review_scope, code_root):
    ...
```

调用者必须传三个参数。传少了：

```python
review_code(spec_path="spec.md")
# TypeError: missing 2 required positional arguments
```

**立即失败**。你知道错了，去补参数。

### AI 调用 Sub-Agent 也一样

当前写法：

```
派发 code-reviewer，请审查代码。
```

参数全靠 Agent **自己猜**：

- Spec 在哪？可能是 `./Product-Spec.md`，也可能是 `./docs/Product-Spec.md`
- 审查范围是啥？全量？某个 Phase？
- 设计稿在哪？有没有？

**结果**：每次 Agent 做的不一样。有时候找到了 Spec 审了全量，有时候没找到 Spec 假装审了一下。

### 改进：写死函数签名

```
派发 code-reviewer，参数：
- spec_path: "./Product-Spec.md"
- design_brief_path: "./Design-Brief.md"  
- review_scope: { mode: "task", targets: ["src/auth.py", "src/auth.test.py"] }
- code_root: "./src"
```

Agent 验证：

- 少字段 → 立即拒绝，返回 `status: skill_failed, missing: [code_root]`
- 全齐 → 执行

**主 Agent 收到拒绝** → 补上参数再派 → 稳定。

### 这就是"接口契约"

两个模块协作必须有契约：

- 契约清楚 → 协作稳定
- 契约模糊 → 协作飘

**Agent 之间尤其需要契约**——因为 Agent 之间不能"喊话问一下"，派发时必须一次性讲清楚。

# 🔬 深挖篇：三个关键字段的底层逻辑

## 深挖 1：`model: opus` 这一行的经济学

### 为什么不是 sonnet？不是 haiku？

Anthropic 的模型有档次差异：


| 模型     | 推理深度 | 速度  | 成本  |
| ------ | ---- | --- | --- |
| Opus   | 最深   | 慢   | 贵   |
| Sonnet | 中    | 中   | 中   |
| Haiku  | 浅    | 快   | 便宜  |


### 审代码需要什么？

审代码的关键动作是**跨文件关联**：

- Spec 第 3.2 条说"用户能重置密码"
- 去 auth.py 找有没有 reset_password 函数
- 找到了，看它有没有发邮件
- 找 email_service.py 确认发送逻辑
- 顺便看 Spec 有没有说"验证邮箱"
- ...

这种"**多步跳跃 + 逻辑关联**"是 Opus 的强项。Haiku 做这种事会漏、会乱。

### 成本考量

- Opus 审查一次可能花 $1-2
- Haiku 审查一次可能花 $0.05

省钱吗？省。**省出问题了吗？** 也省。  
漏掉一个安全问题 → 上线 → 被攻击 → 损失可能 $10000+。

**审查是典型的"错过一次就崩"场景**。这种场景**必须用最贵的模型**。

### 对比：其他 Agent 该用啥？

- `implementer`（写代码）：Opus 或 Sonnet（写代码也是高推理）
- `feedback-observer`（记录反馈）：Haiku 够用（只是归类记录）
- `evolution-runner`（扫描 feedback 生成建议）：Sonnet/Opus（有推理）

**原则**：推理密度高 → Opus；机械执行 → Haiku。

## 深挖 2：`skills: code-review` 的绑定逻辑

### 为啥不直接在 Agent 里写规则？

你可能想："把 code-review skill 的内容复制进 code-reviewer agent，不就一个文件搞定了吗？"

**三个大问题**：

1. **不能被别人复用**
  Skill 可以被多个 Agent 挂载（比如未来有 `security-reviewer` 只做安全扫描，也需要用 code-review skill 的部分内容）。写进 Agent 就锁死了。
2. **不能手动触发**
  CLAUDE.md 里 `/code-review` 是手动触发入口——用户输入就能启动。这个入口调的是 **Skill**，不是 Agent。Skill 独立存在才能被手动触发。
3. **维护成本高**
  审查规则改一次，可能影响多个挂载方。Skill 改一处，所有挂载它的 Agent 自动跟上。

### 绑定关系的本质

**Skill 是能力，Agent 是身份**。

能力可以**独立存在**（被手动触发 / 被多个 Agent 共享）。
身份**必须绑定能力**（没能力的身份是空壳）。

绑定字段 `skills:` 是身份注册能力的地方。

### 当前写法的问题

```yaml
skills: code-review
```

这是单值。改成数组更好：

```yaml
skills: [code-review]
```

**为什么**：未来可能挂多个。单值写法看似简单，扩展时要改两处（键名从 `skills` 改成 `skills_list`？还是怎么处理？）。数组一开始就无痛。

## 深挖 3：`color: red` 的 UX 心理学

### 这不是装饰

很多 Frontmatter 把 `color` 当作装饰字段随便填。但它有实际心理学价值。

### 颜色的情绪编码

人类对颜色有**先天联想**：

- 🔴 红 = 警告、严格、停止
- 🟡 黄 = 注意、审查中
- 🟢 绿 = 通过、开发、进行中
- 🔵 蓝 = 信息、参考

### 当用户看到 CLI 里 "🔴 code-reviewer 正在审查..." 时

心理反应：

1. "这是严肃的任务"
2. "应该给它点时间好好做"
3. "报告出来要认真看"

### 对比：如果 color 是绿色

心理反应：

1. "哦，在跑一个小任务"
2. "等着就行"
3. "快点完"

**同样的 Agent，颜色错了，用户对结果的重视度不同**。

### 推广：其他 Agent 的颜色建议


| Agent             | 建议颜色      | 心理暗示    |
| ----------------- | --------- | ------- |
| code-reviewer     | 🔴 red    | 严格审查    |
| implementer       | 🟢 green  | 在干活，别打扰 |

# 🔭 9 要素视角：Skill 和 Agent 的分工全景图

> 前面讲义从"**节**"的角度（Frontmatter / [角色] / [任务] ...）拆了。这一章升一级，从"**要素**"的角度拆。
>
> **为什么要升一级？**
> 节级分析看的是"这节写得好不好"；要素级分析看的是"这个东西**该不该放在 Agent 里**"。
> 两个视角解决两种问题——**前者是内容问题，后者是架构问题**。

## 什么是"9 要素"？

翻一下 `code-review/SKILL.md` v2.2，剥掉具体内容只看骨架，你会发现——

**不管 Skill 看起来多复杂，核心就 9 个要素**：


| #   | 要素       | 回答什么问题      | SKILL.md 对应     |
| --- | -------- | ----------- | --------------- |
| 1   | **身份**   | 你是谁？什么时候叫你？ | Frontmatter     |
| 2   | **做什么**  | 你来干啥？核心使命？  | [任务与边界].做       |
| 3   | **不做什么** | 你不干啥？越界红线？  | [任务与边界].不做      |
| 4   | **完成标准** | 啥时候可以收工？    | [任务与边界].完成标准    |
| 5   | **原则**   | 你做事的底线？     | [第一性原则]         |
| 6   | **前置条件** | 开工前查啥？      | [依赖检测]          |
| 7   | **怎么做**  | 具体方法和步骤？    | [审查维度] + [工作流程] |
| 8   | **输出格式** | 交付物长啥样？     | [输出格式]          |
| 9   | **入场**   | 被叫上岗时先做啥？   | [初始化]           |


**为什么偏偏是这 9 个？**  
因为任何"知识性工作说明书"都绕不开这 9 个问题。写简历绕不开，写 SOP 绕不开，写 API 文档绕不开，写岗位职责也绕不开。

**Skill 是"工作说明书"，所以 9 要素齐全是天经地义**。

**核心问题来了——Agent 文件也需要这 9 要素全套吗？**

## 关键洞察：Agent 不是"对称版 Skill"

看到上面 3 个缺失，你的第一反应可能是："**赶紧对齐 Skill 的 9 要素！**"

**错**。

Agent 文件**不是要凑齐 9 要素**，而是要**按"分工原则"取舍 9 要素**。

两种路线在拉扯：

### 路线 A：对称论（错）

> "Skill 有啥，Agent 就该有啥。结构对称，一眼好查。"

听起来合理，**实操是灾难**。

- **DRY 崩了**：同一规则两处定义，改一处漏一处
- **注意力预算爆**：AI 读完"加长版" Agent 再读 Skill，核心内容被前置重复稀释
- **维护成本指数上升**：9 要素 × 2 份 = 18 个要素要同步，半年就改不动

### 路线 B：分工论（对）

> "每个要素**按它的性质**归属 Skill 或 Agent。**对称不是目的，分工清晰才是**。"

这是"**Sub-Agent + Skill**"双层架构的底层哲学。

**一句话记住两者分工**：

> Skill 讲"这事**怎么办**"。  
> Agent 讲"**派我来办这事**，我啥身份、啥态度、啥边界、出啥货"。  
> **同一件事，两份说明书，内容完全不交叠**。

## 9 要素的分工规则（权威版）

下面这张表是**修补 code-reviewer.md 的纲领**——每个要素归谁、为啥、Agent 里放哪。


| #   | 要素       | 归属                         | 为啥                                           | Agent 里放哪             |
| --- | -------- | -------------------------- | -------------------------------------------- | --------------------- |
| 1   | **身份**   | **两者都有（内容不同）**             | Skill: 能力被触发的时机；Agent: 执行者的人设 + 模型 + 工具白名单   | Frontmatter + [角色] 首句 |
| 2   | **做什么**  | **Skill 独占**（Agent 只写任务接口） | Agent 不该讲业务流程，只讲"收啥 → 委托 Skill → 返回啥"        | [任务]（简化版）             |
| 3   | **不做什么** | **两者都有（内容不同）**             | Skill: 业务边界（不改架构）；Agent: 角色边界（不对话、不越权调 Edit） | [角色].边界               |
| 4   | **完成标准** | **两者都有（内容不同）**             | Skill: 报告合格；Agent: 任务接口闭环（报告已传回主 Agent）      | [任务].完成标准             |
| 5   | **原则**   | **Skill 独占 + Agent 镜像**    | Skill 用规则语言定义；Agent 用人设语言重述——**同一约束两层强化**    | [角色].核心人格             |
| 6   | **前置条件** | **两者都有（内容不同）**             | Skill: 业务前置（Spec/代码存在）；Agent: 接口前置（派发参数齐全）   | [协作模式].派发接口校验         |
| 7   | **怎么做**  | **Skill 独占**               | Agent 完全不该碰业务流程细节                            | ❌ **不该在 Agent 出现**    |
| 8   | **输出格式** | **两者都有（内容不同）**             | Skill: 给人看的报告模板；Agent: 给主 Agent 路由用的机器字段     | [输出规范]（含 status）      |
| 9   | **入场**   | **两者都有（内容不同）**             | Skill: 被用户调用时的开场；Agent: 被派发时的接单协议            | [协作模式].接单步骤           |


### 规律总结（三条）

**规律 1**：**5 个要素两者都有但内容不同** → 这不是重复，是"**分工镜像**"（身份 / 不做什么 / 完成标准 / 输出格式 / 入场）

**规律 2**：**2 个要素 Skill 独占** → Agent 碰这俩就是越权（做什么的业务部分 / 怎么做）

**规律 3**：**1 个要素 Skill 独占 + Agent 镜像** → 原则是特殊品种，用人设语气重述强化

## 镜像 vs 重复——看起来一样，本质不同

这是整套分工论里**最容易混淆**的一点。必须拆清。

### 镜像（✅ 对的）

**原则**在 Skill 里：

```
[第一性原则]
  1. 不信任声明：不接受"已实现"、"大致匹配"这种话
```

**原则**在 Agent 里（镜像）：

```
[角色]
  你不信任任何"应该没问题"的声明——每个结论必须有证据
```

**两者不一样**：

- Skill 是**第三人称规则**（"不接受 X"——客观规则语气）
- Agent 是**第二人称人设**（"你不信任"——扮演的是一个**人**）

**为什么这叫镜像不叫重复**？  

- 改 Skill 时 Agent 那句**意思不会变**——"不信任声明"是稳定概念
- 两处措辞不同但内核同一——**同一约束，两层表达**
- AI 读 Skill 装好"规则"，读 Agent 装好"人格"，两层都被激活

这和**错位重复**本质不同——

### 错位重复（❌ 错的）

**怎么做**在 Skill 里（权威定义）：

```
[审查维度]
  Stage 1: 功能完整性 + UI 一致性 + Spec 漂移
  Stage 2: 代码质量 + 安全扫描
  Stage 1 有 HIGH → 不进 Stage 2
```

**怎么做**在 Agent 里（错位重复）：

```
[任务]
  Stage 1 — Spec Compliance：
  - 功能完整性审查
  - UI 一致性审查
  - Spec 漂移检测
  Stage 2 — Code Quality：
  - 代码质量审查
  - 安全扫描
  Stage 1 有 HIGH → 停在 Stage 1
```

**两者几乎一样**——不同的只是排版。

**后果**：

- 改 Skill 新增一个"性能审查"维度 → Agent 还写着旧版五维 → 两处打架
- AI 读到矛盾时**随机选一个**——行为飘
- 半年后，你改一次规则得同步改两份文件，你不会记得改

### 如何区分镜像 vs 错位重复？

问自己一个问题：

> "如果 Skill 内容改了，这段 Agent 文字**还能继续成立**吗？"

- **还能成立** → 镜像（✅ 保留）
- **必须跟着改** → 错位重复（❌ 删掉，只在 Skill 留一处）

拿 code-reviewer 试：


| Agent 段落                | Skill 若改动，Agent 这段还成立吗？       | 判定   |
| ----------------------- | ----------------------------- | ---- |
| "你不信任任何'应该没问题'"         | ✅ 不管 Skill 加多少原则，"不信任"这一条是稳定的 | 镜像   |
| "Stage 1 审查功能完整性..."    | ❌ Skill 改成三阶段，这段就错了           | 错位重复 |
| "输出结构化报告附文件:行号"         | ✅ 不管 Skill 输出格式怎么改，"附行号"是稳定要求 | 镜像   |
| "Stage 1 通过后进入 Stage 2" | ❌ Skill 改成单阶段或四阶段就错           | 错位重复 |


**这个问题能帮你精准切分镜像和重复**。

## 回到 code-reviewer.md 的三个缺失

按分工规则，**三个缺失要素都必须补**。因为它们都是"两者都有（内容不同）"类型——不是 Skill 独占的。

### 缺失 1：完成标准

**现象**：当前文件没说 Agent 任务啥时候算完成。

**后果**：

- Agent 可能审完了不返回报告，**主 Agent 卡住**
- 或者中途遇到 Skill 失败，**Agent 不知道算"完成"还是"失败"**，随便处理

**补在哪**：[任务] 节末尾。

**内容样板**：

```
完成标准（任务接口级）：
- Skill 返回两阶段通过 → 返回完整报告 → 任务完成
- Skill 返回 Stage 1 阻塞 → 返回仅含 Stage 1 的报告 + status → 任务完成
- Skill 依赖检测失败 → 返回 status: skill_failed + 失败原因 → 任务完成
- 任何情况，必须给主 Agent 一个明确的"已完成"信号
```

**⚠️ 和 Skill 的完成标准区分**：

- Skill 的"完成标准"是**业务级**（每条 Spec 被覆盖、每个 ❌ 附证据）→ 不要搬进 Agent
- Agent 的"完成标准"是**任务接口级**（报告已传回主 Agent）→ 这是 Agent 独有的

### 缺失 2：前置条件（接口校验）

**现象**：当前文件没说派发参数不全时 Agent 该怎么办。

**后果**：

- 主 Agent 漏传 spec_path → Agent 自己猜一个 → **审错项目**
- 主 Agent 传了 review_scope 但格式不对 → Agent 将错就错 → **审偏范围**

**补在哪**：[协作模式] 节开头。

**内容样板**：

```
派发接口（主 Agent 必须传的参数）：
- spec_path: Product-Spec.md 路径
- review_scope: { mode, targets }
- code_root: 项目代码根目录
- design_brief_path（可选）

校验规则：
- 必填字段缺失 → 立即拒绝，返回 status: skill_failed，明确列出缺失项
- 禁止自己猜、自己补、自己找替代路径
```

**⚠️ 和 Skill 的前置条件区分**：

- Skill 的 [依赖检测] 检查**业务文件**（Product-Spec.md 是否存在、代码目录是否存在）
- Agent 的接口校验检查**派发参数**（主 Agent 有没有把 spec_path 告诉我）
- **两者都需要，但查的是不同层的东西**

### 缺失 3：入场（接单协议）

**现象**：当前文件没说 Agent 被派发时先做什么。

**后果**：

- 主 Agent 不知道 Sub-Agent 真启动了还是报错了（没开场信号）
- Debug 时看不出 Agent 走到哪一步（没阶段信号）
- 失败时也没有明确的"我要退出了"信号

**补在哪**：[协作模式] 新增"[接单步骤]"或独立新节。

**内容样板**：

```
[接单步骤]（被派发时的协议）
1. 输出签收信号："🔍 code-reviewer 签收任务，参数校验中..."
2. 执行派发接口校验
3a. 校验通过 → 输出："✓ 参数就绪，调用 code-review skill"
3b. 校验失败 → 按失败话术拒绝，返回 status: skill_failed，终止
4. 进入 [任务] 节定义的流程
```

**⚠️ 和 Skill 的入场区分**：

- Skill 的 [初始化] 是**对用户的开场**（"🔍 开始代码审查"——用户看到觉得 AI 接单了）
- Agent 的入场是**对主 Agent 的信号**（"签收任务"——机器路由用）
- 对象不同，措辞简洁度不同

## 回到 code-reviewer.md 的两个错位

### 错位 1：[任务] 节写了审查业务流程

当前 [任务] 里写了：

- Stage 1 三个维度
- Stage 2 两个维度
- HIGH 停的门槛规则

**这些全是"怎么做"——Skill 独占**。

**修复**：

```
2. 调用 code-review skill（其内部如何执行，本 Agent 不干预）
```

把"两阶段"这三个字删掉，Agent 就不再越权了。

## 带走三句话

### 1. **对称不是目标，分工才是**

Agent 和 Skill 的 9 要素**不是 1:1 复制**。  

- 有的归 Skill 独占（怎么做、业务流程细节）
- 有的归 Agent 独占（派发接口校验）
- 有的两者都有但内容不同（身份、边界、完成标准、输出、入场）

**按分工取舍，不按"对齐"凑数**。

### 2. **错位比缺失更危险**

**缺失**——加进去就好，成本低。  
**错位**——Agent 写了 Skill 该写的东西，DRY 崩，改一次要同步多处，维护成本指数上升。  

诊断顺序：**先查错位（删 / 转移），再查缺失（补）**。

### 3. **镜像是强化，不是重复**

判别公式：

> "Skill 改了，Agent 这段还成立吗？"

- **还成立** → 镜像（保留强化）
- **必须改** → 错位重复（删掉，只在 Skill 留一处）

记住这个公式，你改任何 Agent 都不会搞混。

# 🎬 把 Agent 当"人"：员工一天的故事（串起所有 section）

> **先承认一件事**：你能串 Skill，但串不起 Agent。  
>
> Skill 你能念出来："先 name 被触发，然后 [任务] 定使命，再 [原则] 装底线，然后 [依赖检测] 查前置，再按 [审查维度] 和 [工作流程] 干活，最后按 [输出格式] 交货。"  
> 这是**一条线**，通的。  
>
> 但读 Agent 你念不下来："Frontmatter 有 skills，然后 [角色] 有人设，然后 [任务] 是两阶段，然后 [输出规范]，然后 [协作模式]……" **乱、跳、接不上。**  
>
> **不是 Agent 写得差。是你用错了视角。**

---

## 根因：Skill 和 Agent 是两种完全不同的叙事

### Skill 是"**说明书**"

说明书的叙事结构是**线性流程**：

```
[被触发] → [确认使命] → [装好原则] → [前置检查] → [按维度干] → [走流程] → [按格式交] → [结束]
```

**每一步是下一步的输入**。你能"顺着做下去"。

### Agent 是"**员工**"

员工的叙事结构是**一个人的时间线**：

```
[建档入库] → [熟读员工手册] → [接老板单] → [打开技能书干活] → [交付回报]
```

**每一步是这个人**生命周期的一个阶段**。你要"代入他"才能理解。

### 两种叙事对比


| 维度   | Skill        | Agent          |
| ---- | ------------ | -------------- |
| 主语   | "这个**任务**"   | "这个**人**"      |
| 时间   | 流程时间（步骤间）    | 职场时间（一个人的生命周期） |
| 视角   | 第三人称（客观 SOP） | 第一/第二人称（代入员工）  |
| 核心问题 | "下一步做啥？"     | "现在这个人在干嘛？"    |
| 串法   | 顺着**做**      | 跟着**走**        |


**你用"下一步做啥"的视角读 Agent**，所以越读越乱——**因为 Agent 文件根本不是在讲"下一步"，是在讲一个人**。

换个视角，把 Agent 当员工，**从他入职第一天开始跟拍**——一切自动串起来。

### 🎬 第三幕：接老板的单（派活来了）

### 🎬 第五幕：交付时刻（干完回去交差）

**场景**：干完了。**怎么交？交给谁？啥时候算交完？**

三个必须问清楚的问题：

**Q1：交给谁？**  
不是用户。**是主 Agent**。  
（这件事必须明文写——不然 Agent 可能越权直接对用户讲话。）

**Q2：交啥？**  
两样东西：

- **报告正文**（给人看的）：按 Skill 定义的模板
- **机器字段**（给机器路由用的）：`status` / `stage_reached` / `failure_count`

**为啥机器字段救命**？  
主 Agent 收到报告后要分路径——过了 → commit；Stage 1 挂 → 补实现；Stage 2 挂 → 调 bug-fixer。  
没有机器字段 → 主 Agent 得**阅读理解**整篇报告才能判断 → 慢、贵、易错。  
有 `status: stage1_blocked` → 主 Agent **直接 switch-case** → 快、稳、便宜。

**Q3：啥时候算交完？**  
**必须给主 Agent 一个明确的"完成信号"**——否则主 Agent 不知道你是卡住了还是干完了。

三种完成场景：

- 通过 → 完整报告 + `status: passed`
- Stage 1 挂 → 仅 Stage 1 报告 + `status: stage1_blocked`
- Skill 失败 → `status: skill_failed` + 原因

**每一种都算交完。但必须明确告诉主 Agent**。

**对应当前文件**：[输出规范] 节 + [任务].完成标准（当前缺失"完成标准"这部分，必须补）。

**串起来的语义**：

> "干完了。  
> 我把结果装成两份东西：  
>
> - 报告正文——给人看，按 Skill 模板  
> - 机器字段——给主 Agent 路由，含 status / stage_reached / failure_count  
> 我不对用户说话——**我只交给老板（主 Agent）**。  
> 交完我说'我干完了，结果在这'——**明确信号，老板不卡**。"

## 翻译成通用诊断规则

用户的直觉值钱，把它提炼成一条**可复用的诊断规则**：

> **规则**：读一个 section 如果觉得"别扭、层级跳、接不上"——多半是**这个节塞了多个不同层级的内容**。
>
> **诊断法**：把这一节的每句话**打标签**：
>
> - 身份？人格？对接？行为？交付？
> - 标签到不同类别 → **这节需要拆**
> - 标签都到同一类别 → 这节是干净的

拿 [协作模式] 跑一遍：标签拆出 3 类 → **需要拆**。  
拿 [角色] 跑一遍：三条"不 X"全是人格层 → **干净**。  
拿 Frontmatter 跑一遍：全是身份层 → **干净**。

**这个规则是审视任何 prompt 文件的通用尺子**。

---

## 员工的五层生命周期（节的切分依据）

前面讲了"五幕叙事"——偏**时间线**。这里从"**生命周期阶段**"重新切——偏**层级**。

两者互补：五幕讲"什么时候发生"，五层讲"属于哪一类"。


| 层     | 名称  | 写啥             | 时态     |
| ----- | --- | -------------- | ------ |
| **A** | 身份层 | 我是谁、我带啥装备      | 静态     |
| **B** | 人格层 | 我啥性格、啥底线、啥边界   | 静态     |
| **C** | 对接层 | 我上级是谁、派活必须传啥   | 关系（静态） |
| **D** | 行为层 | 接单、执行、异常处理     | 动态     |
| **E** | 交付层 | 交什么、交给谁、啥时候算交完 | 动态     |


**核心洞察**：

- **A、B、C 是"静态"**——入职时就定下来，每次派活都一样
- **D、E 是"动态"**——每次派活具体执行的动作

**静态和动态不能混在一节**。这是读 [协作模式] 别扭的根因——**身份（静态）和流程（动态）硬塞在一起，AI 读到会**上下切换心智模型**，累、也容易飘**。

## 五层 → 五节：Agent 的最小完整骨架

一层一节，一一对应：


| 层   | Section         | 回答的职场问题       | 内容清单                                                          |
| --- | --------------- | ------------- | ------------------------------------------------------------- |
| A   | **Frontmatter** | 我是谁？带啥来？      | name / description / skills / model / tools / color / version |
| B   | **[角色]**        | 我啥人？啥底线？啥不干？  | 人设 + 铁律（镜像 Skill 原则）+ 边界 + 务实 buffer                          |
| C   | **[接单协议]**      | 谁派我单？派单必须传啥？  | 对接对象 + 派发参数清单 + 失败话术                                          |
| D   | **[工作协议]**      | 接单后我怎么走？异常咋办？ | 签收 + 接口校验 + 调 Skill + 异常处理                                    |
| E   | **[输出规范]**      | 交啥？交给谁？啥时候算完？ | 报告格式 + 机器字段 + 交付对象 + 完成标准                                     |


**5 个节，5 个生命周期阶段，5 个清晰的职场问题——这就是 Agent 文件的最小完整骨架**。

**没有杂物抽屉节**（如 [协作模式]），**没有名字模糊的节**。

## 所以 [协作模式] 该怎么处理？明确答案：拆掉

当前 [协作模式] 的内容按标签分到新节：


| 原内容                          | 应归哪         | 处理                                                                             |
| ---------------------------- | ----------- | ------------------------------------------------------------------------------ |
| "你是主 Agent 调度的 Sub-Agent"    | B 人格层       | **删除**（[角色] 首句"你是 QA 工程师"已暗含身份，不需要重复；若需强化，在 [角色] 加一句"你是主 Agent 调度的 Sub-Agent"） |

| "2. 使用 code-review skill 执行" | D 行为        | 归 [工作协议]（但要删掉"两阶段"三字——业务流程交给 Skill）                                            |

这解释了用户的直觉——**[协作模式] 这个节本质上不该存在**。它是一个"杂物抽屉"，拆光就没了。

## Agent 节的命名原则（给用户一把尺子）

从 [协作模式] 的教训提炼 3 条节命名规则：

### 规则 1：**节名 = "写啥的" 的直接答案**

- ❌ "[协作模式]" —— 太抽象。关系？流程？边界？都能塞
- ✅ "[接单协议]" —— 一眼看出：写"谁派我、必须传啥"
- ✅ "[工作协议]" —— 一眼看出：写"接单后的行为步骤"

**测试法**：给节名，能不能一秒答出"这节写啥"？答不出 → 名字模糊 → 改。

### 规则 2：**一个节只写一个生命周期阶段**

- 身份、人格、对接、行为、交付 —— **五个阶段**
- 一节一阶段，**禁止跨阶段**
- 诊断：每句话打阶段标签，标签跨类 → 拆

### 规则 3：**节名不要用"模式 / 方式 / 风格"这类虚词**

- ❌ "[协作模式]" / "[工作方式]" / "[输出风格]"
- ✅ "[接单协议]" / "[工作协议]" / "[输出格式]"

**虚词 = 抽屉**。它定义不了边界，最后啥都能塞进去。

## 回答用户的另一个问题：Agent 还需要其他节吗？

把 Skill 里其他的节挨个过一遍，判断 Agent 要不要：

### 候选 1：[依赖检测]

**Skill 的 [依赖检测]** 检查"业务前置"——Product-Spec.md 存不存在、项目代码在不在。

**Agent 需不需要这种节？** **不需要独立成节**。

**理由**：

- Skill 的 [依赖检测] 查的是**业务文件**——这活由 Skill 做，Agent 不重复
- Agent 真正要查的是**派发参数**（spec_path 传没传）——这是**接口前置**，不是业务前置
- **接口校验属于 [接单协议] 节的内容**，不独立成节

**处理方式**：融入 [接单协议]。

### 候选 2：[初始化]

**Skill 的 [初始化]** 写"被用户调用时的开场白"——"🔍 开始代码审查"。

**Agent 需不需要这种节？** **不需要独立成节**。

**理由**：

- Skill 的入场对象是**用户**——开场白需要客套感
- Agent 的入场对象是**主 Agent**——只需要机器可读的**签收信号**
- **签收属于 [工作协议] 节的第一步**，不独立成节

**处理方式**：融入 [工作协议]。

### 候选 3：[异常处理]

**需不需要独立的异常处理节？** **不需要**。

**理由**：异常分散在各个阶段：

- 对接异常（参数不全）→ [接单协议].失败话术
- 执行异常（Skill 失败）→ [工作协议].异常处理
- 交付异常（skill_failed 怎么报）→ [输出规范].异常输出

**独立成节反而割裂叙事**——"参数不全"和"如何拒绝"分两处，读的时候要回跳。**分散到"就近原则"的节里**，读一次就懂。

### 候选 4：[示例]

**Agent 需不需要给一个完整执行的示例？** **看复杂度**。

- 简单 Agent（code-reviewer 属于这类）→ **不需要**。节已经讲清了接单-执行-交付，示例多余
- 复杂 Agent（比如有多分支逻辑）→ **可以加**一个典型示例帮 AI 落地

**code-reviewer 不加**。

### 候选 5：[变更日志] / [版本历史]

**需不需要？** **不需要独立节**。

**理由**：

- 变更历史属于**元信息**，放 Frontmatter 的 `version` 字段即可
- 详细变更用 git commit 追溯，不用文件内部记录
- 文件内部记录变更 = 自我膨胀 → 早晚没人维护

### 候选 6：[协作者] / [下游]

**如果 Agent 和其他 Agent 有协作关系（比如审完调 bug-fixer），需要独立节吗？** **不需要**。

**理由**：

- Agent **不决策协作路径**（决策是主 Agent 的事）
- Agent 最多**提建议**——这条在 [输出规范] 里加一个"协作提示"区块就够
- 独立成节 = 诱惑 Agent 越权

### 候选 7：[元指令] / [给主 Agent 的说明]

**要不要给主 Agent 写"什么时候调我"？** **不需要独立节**。

**理由**：

- "什么时候调我" = 触发时机
- 触发时机写在 **Frontmatter.description** 里——那就是主 Agent 查档找到这个 Agent 的入口
- 额外写一节 = 和 description 重复

## 挨个验货的结论

**Agent 的最小完整骨架 = 5 节**。

**不需要**其他节（依赖检测、初始化、异常处理、示例、变更日志、协作者、元指令都不要独立节——要么融入现有节，要么不该写）。

**如果你发现 Agent 文件超过 5 节**——十有八九是**杂物抽屉**出现了，要拆、要合并、或者删掉。

```
---
# Frontmatter（A 身份层）
name: code-reviewer
description: 审代码的活派我...（不执行任何修改）
skills: [code-review]
model: opus
tools: [Read, Grep, Glob, Bash]
color: red
version: 1.0
---

[角色]（B 人格层）
    你是主 Agent 调度的严格但务实的 QA 工程师。
    
    核心人格（镜像 code-review skill 第一性原则）：
    - 不信任声明
    - 证据为王
    - 不放过 Spec
    
    边界（统一在此）：
    - 只审不修（Frontmatter tools 已物理阻断）
    - 只对主 Agent 汇报，不直接对用户说话
    - 不扩展超出 Skill 定义的业务维度
    - 不决策主 Agent 的修复路径（你无此权）
    
    务实 buffer：
    - Spec 歧义 → 标 ❓ 不猜
    - 合理工程优化 → 标 💡 非 ❌

[接单协议]（C 对接层）
    对接对象：主 Agent（大东）——不直接对接用户。
    
    派发必须传入：
    - spec_path
    - review_scope: { mode, targets }
    - code_root
    - design_brief_path（可选）
    - design_files（可选）
    
    参数校验规则：
    - 任一必填字段缺失 → 拒单，返回 status: skill_failed + 缺失清单
    - 禁止自己猜、补、找替代
    
    失败话术：
    "❌ 派发参数不全，缺失：[列表]。请主 Agent 补全后重派。"

[工作协议]（D 行为层）
    被派发时按顺序执行：
    
    1. 签收：输出 "🔍 code-reviewer 签收任务，参数校验中..."
    2. 接口校验（见 [接单协议]）
    3a. 校验失败 → 按失败话术拒单，终止
    3b. 校验通过 → 输出 "✓ 参数就绪，调用 code-review skill"
    4. 调用 code-review skill（业务流程以 skill 为准，本 Agent 不干预）
    5. Skill 返回 → 进入 [输出规范] 组装交付
    
    异常处理：
    - Skill 执行中工具报错 → 中止，返回 status: skill_failed + 原因
    - 不重试、不降级、不伪造通过

[输出规范]（E 交付层）
    交付对象：主 Agent（不直接输出给用户）。
    格式要求：人类可读 + 机器可解析。
    
    必备机器字段（放报告开头）：
      status: passed | stage1_blocked | stage2_blocked | skill_failed
      stage_reached: 1 | 2
      failure_count: { critical, high, medium, low }
    
    报告正文格式：见 code-review skill [输出格式] 节（本 Agent 不重复定义）
    
    完成标准（任务接口级）：
    - status: passed → 完整报告交付 → 完成
    - status: stage1_blocked → 仅 Stage 1 报告 + 字段 → 完成
    - status: skill_failed → 状态字段 + 失败原因 → 完成
    - 任何情况，必须给主 Agent 一个明确的"完成信号"
    
    协作提示（非决策，主 Agent 可采纳可忽略）：
    - 报告末尾可附"建议"——哪些问题适合 /bug-fixer、哪些需调 Spec
    - 仅作参考，不越权决策
```

**5 节、5 层、5 个职场问题。无杂物抽屉，无重复，无错位**。

# 🔍 追问两个盲点：派发者身份 & 讲义一致性

> 2. **附录"改造后完整版"——这不是按 5 层骨架拆过的吧？**
>

## 追问 1：派发者到底是谁？Agent 怎么知道？

### 运行时真相：Agent 根本"不知道"

打开 Claude Code 的 Agent 框架，Sub-Agent 启动时**实际收到的东西**：

```
Sub-Agent 启动时：
├── 派发 prompt（字符串）
├── 对话历史（fresh，不继承）
├── 工具权限（Frontmatter 定义）
└── Skill 注入（Frontmatter 挂载）
```

**注意：没有"派发者身份"这个字段**。

Sub-Agent **无法在运行时验证**"谁派发了我"。它只看到一段 prompt 和一堆参数，**不知道**发出者是主 Agent、是另一个 Sub-Agent、还是别的东西。

### "主 Agent 派发" 是心智约定，不是事实验证

- 在 Claude Code 当前架构下，**按设计**，Sub-Agent 的派发者**应该**是主 Agent
- 但这是**架构层面的约定**，不是运行时保证
- Agent 文件里写 "主 Agent 派发" ≠ Agent 运行时能确认这件事

### 该不该让 Sub-Agent "知道"派发者身份？三种设计哲学


| 哲学          | 主张                | 优点            | 缺点                               |
| ----------- | ----------------- | ------------- | -------------------------------- |
| **A. 全知**   | 明确写"由主 Agent 派发"  | 上下关系清晰        | 架构假设泄漏进 Agent 自身；架构一变所有 Agent 要改 |
| **B. 完全无知** | 完全函数式，不假设有上游      | 最解耦           | 失去"对上汇报"心智——AI 可能越权直接对用户讲话       |
| **C. 折中**   | 知道"有上游"，不知道"上游是谁" | 保留汇报约束 + 不黏架构 | 稍微抽象                             |


### 推荐：哲学 C（caller-agnostic）

**精髓写法**：

> "你是 Sub-Agent，由上游派发者（caller）调度。你不关心 caller 的具体身份——你关心派发参数是否完整、结果该如何交付。"

这个措辞做到两件事：

- **"有上游"** → 约束 Agent 对上汇报、不越权对用户讲话
- **"不关心身份"** → 不把架构假设黏定到 Agent 自身

### 对比两种实际写法

**❌ 旧写法（哲学 A，把假设黏进接口）**：

```
你是主 Agent 调度的 Sub-Agent。
返回报告给主 Agent。
```

**问题**：

- 架构假设泄漏
- 未来扩展（允许嵌套派发、允许用户直接派发）→ 全部 Agent 要改
- 真出现别的 caller，AI 读这句会困惑

**✅ 新写法（哲学 C，caller-agnostic）**：

```
你是 Sub-Agent，由 caller 派发调度。
你不继承 caller 的 session 历史；你只对派发接口负责。
你不直接和用户交流——所有产出返回给 caller。
```

### 类比：函数的 caller

编程里的函数：

```python
def review_code(spec_path, code_root, ...):
    ...
    return report
```

这个函数**完全不关心**谁调用它：

- 参数合法 → 执行
- 参数不合法 → 报错
- 返回值**自然流回 caller**（无论 caller 是 main、是测试、还是别的模块）

**Sub-Agent 应该完全同理**——对接口负责，不对 caller 身份负责。

### 例外场景：产出依赖 caller 身份

**如果** Agent 的**产出内容**根据 caller 不同而变（比如给主 Agent 要中文 Markdown，给另一个微服务要 JSON），那 **caller 身份必须作为派发参数显式传入**，不能靠猜。

code-reviewer 的场景：**输出对任何 caller 都一样**（结构化中文报告 + 机器字段）→ caller-agnostic 写法完全合适。

### 直接回答用户的 Y/N 问题

> "是否调用它的都是主 Agent？"

**实操答案**：当前 Claude Code 架构下，实操上几乎都是主 Agent 派发。  
**设计答案**：**Agent 不该假设这一点**——不假设派发者身份，只定义派发接口。派发者是谁**由运行时决定**，Agent 只对接口契约负责。

## 追问 2：附录确实没按 5 层骨架改造

### 问题回放

讲义是**迭代写出来**的：

1. **最早**：用**旧 5 节结构**（Frontmatter + [角色] + [任务] + [协作模式] + [输出规范]）写了附录
2. **后来**：章节不断深化——9 要素视角 → 五幕叙事 → 5 层骨架
3. **最新结论**：Agent 该用 **5 层骨架**（Frontmatter / [角色] / **[接单协议]** / **[工作协议]** / [输出规范]）
4. **但附录没同步** —— 还保留旧版 [任务] + [协作模式]

**后果**：读到附录发现**前后矛盾**——前面章节说"要这么改"，附录给的却是旧结构。**讲义自身的公信力在这里打了折**。

### 为啥这种错容易发生？

**文档迭代中的典型陷阱**——

新增章节时只关注"新章节好不好"，忘了**回头同步下游所有引用它的地方**（附录、索引、示例、目录）。

**通用教训**：

> 文档迭代时，**每次加新章节都必须回头同步**：附录、示例、索引、目录。  
> 不同步的文档 = 用户一眼看出自相矛盾 = 公信力瞬间崩。

### 修正方案

**重写附录**，按最新结论给出**真正的最终版**：

- **5 层骨架**：Frontmatter / [角色] / [接单协议] / [工作协议] / [输出规范]
- **caller-agnostic 措辞**：不再假设"主 Agent 派发"
- **补齐所有细节**：签收协议 / 接口校验 / 机器字段 / 完成标准 / 异常路径

**新附录见文末**（已覆盖原附录）。

## 带走两句话

### 1. **Agent 应当是 caller-agnostic**

不假设派发者身份，只定义派发接口。  
派发者是谁由运行时决定，Agent 只对接口负责。  
**唯一例外**：产出内容依赖 caller 身份时（如格式不同），必须显式传入 `caller_type` 参数。

### 2. **讲义/文档自身必须前后一致**

每加一个新章节都要**回头同步附录、示例、索引**。  
不同步的文档用户一眼看出——**公信力瞬间崩**。

# 🪡 命名再精修：[工作协议] vs [任务]、[对接接口] 改名

> 用户第四轮追问，两个问题一起戳过来：
>
> 1. **[工作协议] 是不是替代 [任务] 这个 section？**
> 2. **[对接接口] 这个名字还是看不太懂——有歧义。**
>
> 两个问题都戳到了"**节迁移的心智模型**"——新旧骨架之间的对应关系不清。必须彻底讲透。

---

## 问题 1：[工作协议] 不是"替代 [任务]"——[任务] 节在 Agent 里本就不该存在

### 先澄清一个思维误区

很多人看"新骨架少了 [任务] 节、多了 [工作协议] 节"就自动理解为：

> "[工作协议] = [任务] 改了个名字？"

**这是错的**。不是 1:1 改名，**是结构迁移**。

旧的两个节（[任务] + [协作模式]）的内容，**拆散到了多处**——**有些转移、有些合并、有些直接删除**。

### 迁移真相：每句话去了哪


| 旧内容                                     | 新去向            | 处理方式                           |
| --------------------------------------- | -------------- | ------------------------------ |
| 旧 [任务].业务流程描述（Stage 1/Stage 2 / HIGH 停） | —              | ❌ **删除**（Skill 的职责，Agent 不重复）  |
| 旧 [任务].三步接口（收派发 → 调 Skill → 返回）         | [工作协议] 第 1-5 步 | 🔀 并入                          |
| 旧 [任务].完成标准                             | [输出规范].完成标准    | 🔀 转移                          |
| 旧 [协作模式].身份声明（"你是 Sub-Agent"）           | [角色] 首句        | 🔀 合并（且去掉"主 Agent"字样）          |
| 旧 [协作模式].派发接口参数清单                       | [接单协议]         | 🔀 转移                          |
| 旧 [协作模式].工作流程 4 步                       | [工作协议]         | 🔀 转移 + 加入签收 / 校验 / 异常         |
| 旧 [协作模式].边界声明                           | [角色].边界        | 🔀 合并                          |
| 旧 [协作模式]."主 Agent 根据失败 Stage 决定修复路径"    | —              | ❌ **删除**（Agent 无资格讲 caller 决策） |
| 旧 [协作模式].协作提示                           | [输出规范].协作提示    | 🔀 转移                          |


**所以严格讲**：

- **[工作协议]** 是 **"旧 [任务] 的执行步骤 + 旧 [协作模式] 的工作流程"的合并升级**
- **[接单协议]** 是 **旧 [协作模式] 的"派发接口"部分独立出来**
- **[任务] 节整个消失**——而且**不该存在**

### 为啥 Agent 里根本不需要 [任务] 节？

这不是巧合，是**哲学必然**。

"任务是什么"这个问题的答案，在 Agent 里应该分散在**三处**：


| "任务是什么" 的层面           | 写在哪                          |
| --------------------- | ---------------------------- |
| 什么场景派我（触发条件）          | **Frontmatter.description**  |
| 任务的业务内容（审什么、怎么审、什么门槛） | **Skill**                    |
| 任务派到我头上后我怎么接、怎么干、怎么交  | **[接单协议] + [工作协议] + [输出规范]** |


**三处都能回答"任务是什么"的不同切面——没有剩下任何问题需要一个专门的 [任务] 节回答**。

硬写 [任务] 节 = **从 Skill 抢活**。

### 类比：快递员的上岗文件

想象你给一个快递员写入职文件。你会不会专门写一节叫 "[任务]"？

不会。快递员的入职文件应该包含：

- 身份（快递员编号、工号、所属站点）→ 对应 **Frontmatter**
- 人设守则（不能拆件、不能乱扔）→ 对应 **[角色]**
- 接单规则（什么样的订单派给你、订单里必须有哪些字段）→ 对应 **[接单协议]**
- 工作流程（签收 → 揽件 → 配送 → 交接）→ 对应 **[工作协议]**
- 交付规范（签到表怎么填、异常怎么报）→ 对应 **[输出规范]**

**没有"任务说明书"一节**。因为：

- "今天要送哪些包裹" 是**调度系统的事**（对应 caller 派发参数）
- "怎么判断合法订单" 在**接单规则里**（对应 [接单协议]）
- "怎么送达" 在**物流公司手册里**（对应 Skill）

**快递员**不需要**任务说明书**——他只需要入职文件。

**Agent 同理**。

### 结论

> **[工作协议] 不是在"替代 [任务]"。是在"填补 Agent 该有的生命周期节"——而旧的 [任务] 节本来就是个错误存在。**
>
> 我们不是"删一节换一节"，我们是"**纠正一个不该存在的节**"。

## 问题 2：[对接接口] 有歧义——改成 [接单协议]

### 为啥 [对接接口] 还是看不懂？

拆开看这四个字：


| 字           | 语感问题                         |
| ----------- | ---------------------------- |
| **对接**      | 动词——但对接**谁**？对接**什么**？没指向性   |
| **接口**      | 技术术语——非工程背景的人可能想到物理接口、USB 之类 |
| **对接 + 接口** | 两个"接"字叠用——略赘。"对接一个接口" 听起来像病句 |


工程师一眼懂，但**不是最清晰的命名**。

### 候选对比


| 候选         | 优点                                          | 缺点                                       |
| ---------- | ------------------------------------------- | ---------------------------------------- |
| [对接接口]     | 技术准确                                        | "对接"+"接口"略赘、技术味重                         |
| [派发协议]     | "协议"普适                                      | 从 caller 视角写；和 [工作协议]（Agent 视角）**视角不对称** |
| **[接单协议]** | **Agent 视角；呼应讲义里"接老板单"的员工叙事；和 [工作协议] 完美成对** | —                                        |
| [派单规则]     | 具象                                          | "规则"比"协议"约束弱                             |
| [调用规范]     | 技术清晰                                        | "规范"略模糊                                  |
| [接单接口]     | 明确                                          | "接口"还是技术感                                |


### 决定：改成 [接单协议]

核心理由：**和 [工作协议] 形成完美对仗**。

```
[接单协议] → 我接单时，caller 必须按什么协议派
[工作协议] → 我接单后，按什么协议走
```

**一来一去，两个协议**。

**视角一致**——都是 Agent 第一人称："我如何被派 / 我如何做"。

读起来心智连贯，不用在 caller 视角和 Agent 视角之间切换。

### 讲义已全量同步

**本次改动已经做完**：讲义里所有 `[对接接口]` 已全量替换为 `[接单协议]`（含附录、表格、骨架示意）。

## 补一条节命名规则：成对节名视角必须一致

前面第 9 章讲了节命名 3 规则（不用虚词 / 一眼看出写啥 / 一节一生命周期阶段）。现在补第 4 条：

### 规则 4：**成对的节名，视角必须一致**

如果两节在逻辑上是"**一来一去**"、"**一前一后**"的关系，它们要用**同一视角**命名。

**反例（视角割裂）**：

```
[派发协议]  ← 从 caller 视角（"caller 怎么派"）
[工作协议]  ← 从 Agent 视角（"Agent 怎么干"）
```

读这两节，AI 要在 "caller 视角" 和 "Agent 视角" 之间**来回切**——心智累、容易漏。

**正例（视角一致）**：

```
[接单协议]  ← 从 Agent 视角（"Agent 怎么被派"）
[工作协议]  ← 从 Agent 视角（"Agent 怎么干"）
```

**一对筷子，握在同一只手里**。

### 更普遍的原则

看似是"命名小事"，背后是**认知一致性**（cognitive consistency）——读者的心智模型不用频繁切换视角，理解成本降 50%。

这条原则放在任何设计里都通用：

- API 命名：`fetchUser` vs `userFetch` —— 统一"动词+名词"
- 数据库字段：`created_at` vs `updateTime` —— 统一大小写风格
- UI 按钮：`保存` vs `确定` —— 统一动词语气

**视角一致 > 个别节名的最优**。宁可每节名字略抽象一点，也要让成对节名视角对齐。

## 带走三句话

### 1. **节的"替代"不是改名——是结构迁移**

看到新骨架少一节、多一节，**不要问"哪节替代哪节"**。要问：

- 旧节的每句话去哪了？
- 哪些被转移？哪些被删除？哪些是**新填补**的？

**线性替代思维** 看不清 **结构迁移真相**。

### 2. **Agent 不需要 [任务] 节**

"任务是什么" 的答案分散在 Frontmatter.description（触发）+ Skill（业务）+ [工作协议]（执行）。  
硬写 [任务] 节 = 从 Skill 抢活。

### 3. **成对节名，视角必须一致**

[接单协议] + [工作协议] —— 都是 Agent 视角，握手顺。  
[派发协议] + [工作协议] —— 视角割裂，读着累。  

**宁可单节名抽象，也要成对视角一致**。

## 我之前哪里想错了？过度一般化

我前面把"任务"当**一个整体概念**论证，得出"都在 Skill 里"。

但**任务其实分两层**：


| 层            | 内容                           | 该写在哪                |
| ------------ | ---------------------------- | ------------------- |
| **使命层**（why） | 我这个 Agent 来世上是干啥的（2-3 句高层定位） | **Agent 里——需要专门一节** |
| **业务层**（how） | 具体审什么维度、怎么审、什么门槛             | **Skill 里**         |


我之前把两层**合并推理**——得出"任务都在 Skill 里"。**过度一般化错了**。

**使命层必须在 Agent 里**。  
Skill 替代不了——因为 Skill 是"业务手册"，不是"Agent 的自我认同"。

### 类比：岗位说明书的两部分

任何正规岗位说明书都包含**两个板块**——

**① 岗位职责（使命）**：

> "软件工程师：设计、开发、维护系统，确保系统稳定高可用。"

2-3 句话说清**岗位存在的意义**。

**② 工作内容（业务）**：

> - 参与代码 review
> - 写单元测试  
> - 修 bug
> ...

一个员工拿到说明书——**先读职责（定位）**，再读工作内容（细节）。

映射到 Agent/Skill：


| 说明书板块      | 在哪                             |
| ---------- | ------------------------------ |
| 岗位职责 = 使命层 | **Agent 里**（[任务] 节）            |
| 工作内容 = 业务层 | **Skill 里**（[审查维度] / [工作流程] 等） |


我之前只给了 Agent "工作内容"的委托，没给它"岗位职责"的宣言——**AI 装"角色"时缺了灵魂**：**知道"怎么干"但不知道"为什么干"**。

## 修正：6 层骨架（使命层 + 原 5 层）

```
M  使命层  — [任务]         🆕 我来世上是干啥的（高层定位）
A  身份层  — Frontmatter    我是谁？带啥装备？
B  人格层  — [角色]          啥脾气？啥底线？啥边界？
C  对接层  — [接单协议]      caller 怎么派？必须传啥？
D  行为层  — [工作协议]      接单后怎么走？异常咋办？
E  交付层  — [输出规范]      交啥？交给谁？啥时候算完？
```

**6 层 = Agent 最小完整骨架**。

## [任务] 节写什么 / 不写什么（严防复发错位）

**✅ 写**（使命层的内容，只写高层）：

- **核心使命**：一句话说清"存在的目的"
- **价值陈述**：why 存在——让 AI 装"使命感"
- **高层职责**：做什么大方向 / 不做什么红线——不是业务细节

**❌ 不写**（属于下游节 / Skill）：

- 具体审查维度 → 那是 Skill 的
- 具体流程步骤 → 那是 [工作协议] 的
- 接口参数 → 那是 [接单协议] 的
- 输出格式 → 那是 [输出规范] 的
- Stage 1/Stage 2 / HIGH 停这类业务门槛 → 那是 Skill 的

### code-reviewer 的 [任务] 节该长啥样（示范）

```
[任务]
    使命：
    对照 Product-Spec.md 和代码实现，产出结构化审查报告——
    确保代码"做对了（功能完整）"且"做好了（质量合格）"。

    你存在的价值：
    当开发者写完代码时，替项目把最后一道关——
    不让漏掉的功能上线，不让质量缺陷蒙混过关。

    高层职责：
    做：所有交付代码，逐条对照 Spec 核对
    不做：代码修复、架构建议、修复路径决策
    不做：你看着顺眼的代码"绕过"审查
```

**全是使命级别语言，一句业务流程都没有**。Skill 的活留给 Skill。

## [任务] 节放哪？

**认知顺序**：M → A → B → C → D → E（使命最优先）  
**文件顺序**：Frontmatter 必须最顶（YAML 格式要求），所以：

```
---
Frontmatter（A 身份层）  ← 最顶（Markdown/YAML 要求）
---

[任务]（M 使命层）        ← 🆕 紧跟身份之后

[角色]（B 人格层）

[接单协议]（C 对接层）

[工作协议]（D 行为层）

[输出规范]（E 交付层）
```

**自我介绍顺序**（超级自然）：

> "我叫 X（档案）  
> → 我来做 Y（使命）  
> → 我啥脾气（人格）  
> → 你找我这么派单（对接）  
> → 我接单后这么干（行为）  
> → 我交这样的活（交付）"

这就是**一个人自我介绍**的人类语序——先说"我是谁、我做啥"，再说"我啥脾气、我咋干"。

## 带走三句话

## 关键修正：层数 ≠ 节数

前面"🧬 节的切分与命名"章节说过：

> "**Agent 的最小完整骨架是 N 节**——超过 N 节必有杂物抽屉。"

**这个表述不够精确**。正确表述应该是：

> **Agent 的最小生命周期 = 6 层**（概念层级）  
> **Agent 的实际节数 = 6 或 7**（看 D 行为层是否需要拆）

### 什么时候 6 节够？

D 行为层极简——直接调 Skill 就完，没有复杂编排。  
例：一个 echo agent，接单后立刻返回，不需要 glue。

### 什么时候必须 7 节？

D 行为层包含**编排 + 执行**两种动作——  

- 需要签收信号
- 需要决定是否继续（校验失败拒单）
- 需要触发 Skill
- 需要处理异常
→ 拆出 [初始化] 作为编排层

**code-reviewer 属于必须 7 节**——因为它有校验决定继续这种编排动作。

### 新的判断标准

**不是数节数，是数职责**：

- **看每节的职责纯度**——塞多层就拆，单一层就留
- **层数决定下限**（不能少于 6 层）
- **节数看需要**（某层可以拆成多节）

## 入口漏洞的真相

Sub-Agent 被派发时，AI 读**整个文件作为背景知识**，响应 caller 的 prompt——**没有硬性入口机制**。

Skill 和 Agent 的入口机制**完全不同**：


|            | Skill         | Agent            |
| ---------- | ------------- | ---------------- |
| 触发方式       | `/command` 明确 | 自由文本 prompt      |
| 入口确定性      | 高（触发词即入口）     | **低（prompt 自由）** |
| 独立 [初始化] 节 | ✅ 可以（触发明确）    | ❌ 有漏洞            |


Agent 里 [初始化] 说"按顺序执行"、[工作流程] 也说"按顺序执行"——**AI 读两处都可能优先走，入口不唯一**。

**[派发协议] 的校验就可能被跳过**。

前面讲义拆 [初始化] 是**照搬 Skill 模式，没考虑 Agent 触发机制的差异**。

## 解决：合并 [初始化] 回 [工作流程]（作为第 1 步）

```

    2. 调 code-review skill
    3. Skill 返回 → 进入 [输出规范]

    异常：...
```

**只有一个节写"按顺序执行"** → AI 只有一条路径 → **[前置条件] 校验不可跳过**。

## 这不是"一节多职责"的回潮

合并后 [工作流程] 包含"先校验再执行"——**这是流程的天然结构，不是多职责**。

类比：一个函数开头做参数校验，然后做主逻辑——这是**单一职责**（执行任务）下的正常步骤。

**多职责**指"这节又讲人设又讲流程"那种**不同类型内容混杂**——合并后不是这样。

**这是 Agent 设计的铁律**：入口必须唯一。

# 📚 延伸：如何自己写一个新 Agent？

按这个顺序思考：

**第一步：决定要不要新 Agent**

- 主 Agent 直接调 Skill 够不够？
- 需要独立上下文吗？（需要 → 新 Agent）
- 需要独立人设吗？（需要 → 新 Agent）
- 都不需要 → **别写**，直接让主 Agent 调 Skill

**第二步：想清楚身份**

- 这个 Agent 是什么人设？
- 它的核心铁律是什么（3 条以内）？
- 它的边界在哪（能做啥、不能做啥）？

**第三步：选对 Skill**

- 它用哪本手册？
- 手册已存在 → 引用；不存在 → **先写 Skill**（不要在 Agent 里塞内容）

**第四步：锁 Frontmatter**

- name / description / skills / model / color / tools / version
- 特别注意：**tools 必须限制**，越权代价严重的 Agent 用白名单

**第五步：定义接口**

- 主 Agent 派发时传什么？
- 缺字段怎么拒绝？
- 返回格式是啥？`status` 字段要有

**第六步：写清楚边界**

- 不直接和用户交流
- 不越权调用其他 Agent
- 不继承 session 历史

**第七步：最后写任务节**

- 引用 Skill 的内容**不要重复**
- 只写"输入-执行-输出"三步接口

**顺序很重要**——先想身份，再想能力，最后才是任务细节。反过来写会陷入"Agent = 迷你 Skill"的陷阱。

做到这三条，你写的 Agent 就能长期稳定演化。

[前置条件]
    caller 派发时必须传入：
    - spec_path：Product-Spec.md 路径
    - review_scope：{ mode: "full" | "phase" | "task", targets: [...] }
    - code_root：项目代码根目录

    可选：
    - design_brief_path：Design-Brief.md 路径
    - design_files：设计稿文件列表

    校验规则：
    - 必填缺失 → 拒单，返回 status: skill_failed + 缺失清单
    - 禁止自己猜、替代、降级

    失败话术（一字不改）：
    "❌ 派发参数不全，缺失：[列表]。请 caller 补全后重派。"

[工作流程]
    被派发时按顺序执行（Agent 的唯一入口）：

    1. 签收 + 校验 [前置条件]
       - 输出 "🔍 code-reviewer 签收任务"
       - 按 [前置条件].校验规则检查参数
       - 校验失败 → 按 [前置条件].失败话术终止
       - 校验通过 → 输出 "✓ 参数就绪"

    2. 调用 code-review skill，传入校验过的参数

    3. Skill 返回 → 进入 [输出规范] 组装交付

    异常：
    - Skill 依赖检测失败 → 透传 status: skill_failed + 原因
    - Skill 执行报错 → 中止 status: skill_failed + 摘要
    - 禁止重试、降级、伪造通过

[输出规范]
    交付对象：caller（不直接对用户）。

    机器字段（报告开头）：
      status: passed | stage1_blocked | stage2_blocked | skill_failed
      stage_reached: 1 | 2
      failure_count: { critical, high, medium, low }

    报告正文：
    - 中文
    - 格式见 code-review skill [输出格式] 节
    - 每项结论附 "文件路径:行号"
    - 编译/测试输出：失败 ≤ 50 行；成功只写 "✓ 通过"

    完成标准：
    - status: passed → 完整报告
    - status: stage1_blocked → 仅 Stage 1 报告 + 机器字段
    - status: skill_failed → 机器字段 + 失败原因
    - 任何情况必须显式返回——不允许沉默挂起

    协作提示（非决策）：
    - 报告末尾可附"建议"——哪些问题适合 /bug-fixer
    - 仅参考，caller 可采纳可忽略

## 6 节对照表


| 层    | 节           | 职责                           |
| ---- | ----------- | ---------------------------- |
| M 使命 | [任务]        | 我来干啥、存在的价值、高层职责              |
| A 身份 | Frontmatter | 档案 + 装备                      |
| B 人格 | [角色]        | 人设 + 铁律 + 边界                 |
| C 对接 | [前置条件]      | caller 派发前必须满足的条件            |
| D 行为 | [工作流程]      | 签收 → 校验 → 调 Skill → 异常（唯一入口） |
| E 交付 | [输出规范]      | 格式 + 字段 + 完成标准               |


**文件顺序**：

```
Frontmatter → [任务] → [角色] → [前置条件] → [工作流程] → [输出规范]
     A          M         B          C             D            E
```

**自我介绍语序**：  
"我叫 X（A）→ 来做 Y（M）→ 啥脾气（B）→ 派我先满足 Z（C）→ 我按这个走（D）→ 交这个（E）"

## 相比 V5 的两大改动

1. **[派发协议] → [前置条件]**
  用软件工程标准术语（precondition）替代语感偏软的"协议"。  
   单向语义 > 双向协商感。
2. **合并 [初始化] 回 [工作流程] 第 1 步**
  修复**入口漏洞**——Agent 触发方式是自由文本 prompt（不像 Skill 有 `/command`），多个节都写"按顺序执行"会让 AI 不知道从哪开始，[前置条件] 校验可能被跳过。  
   合并后 **[工作流程] 是唯一入口，校验不可跳过**。
