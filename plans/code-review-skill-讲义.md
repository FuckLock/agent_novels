# code-review SKILL.md 逐节深度讲解（学生版）

> 这不是实施计划，是教学讲义。目的：帮你彻底看懂每一节的优缺点、是否需要、位置对不对、怎么改。

---

## 先铺垫一下：Skill 本质是什么？

Skill = 给 AI 看的"工作说明书"。
SKILL.md 里每一节都在回答一个问题：

| 节 | 回答什么问题 |
|---|---|
| Frontmatter | 你是谁？什么时候叫你？ |
| [任务] | 你来干啥？ |
| [依赖检测] | 开工前要检查啥？ |
| [第一性原则] | 你做事的底线是啥？ |
| [输出风格] | 你说话啥风格？ |
| [文件结构] | 你家几个文件？ |
| [审查维度清单] | 具体查哪几样？ |
| [审查策略] | 用啥方法查？ |
| [工作流程] | 步骤顺序？ |
| [初始化] | 开机从哪儿开始？ |

---

## 每节讲解的固定格式（你只要记住 6 个问题）

对每一节，我都问这 6 个问题：

1. **它在说啥**（大白话）
2. **好在哪**
3. **差在哪**
4. **咋改 + 为啥改**
5. **要不要**（保留/删除）
6. **位置对不对**（该排第几）

## 节 1：Frontmatter

### 在说啥
Skill 的身份证。告诉系统"我叫什么、什么时候被叫上台"。

### 好在哪
- 格式标准，系统能识别
- description 写"触发时机"（用户说啥词）而不是"我能干啥"——**这对自动路由更有用**

### 差在哪
- 关键词可能**误触发**（用户说"审一下这篇文章"也可能命中）
- 没版本号——改了之后没法追溯
- 没记录依赖的其他 Skill

### 咋改 + 为啥改
加 `version` 和 `depends_on`。
- **为啥加版本**：未来迭代能追溯
- **为啥加依赖**：让主 Agent 能提前判断 Skill 能不能跑

### 要不要
**必须要**。

### 位置对不对
**第 1，对的**。✅（系统要求）

## 节 2：[任务]

### 在说啥
"你这次来干什么活"。一句话定使命。

### 好在哪
- **职责边界清楚**：最后一句"修复由主 Agent 路由"= 明确"我不修代码"

### 差在哪
- "完整度和质量"太虚——**多完整叫完整？**
- 没完成标准——AI 不知道啥时候能收工
- "不做清单"不全——只说不修代码

### 咋改 + 为啥改
改成三块：**做 / 不做 / 完成标准**。
- **为啥分三块**：
  - "做"给正向目标
  - "不做"挡 AI 越界（AI 爱热情过头帮忙修 bug）
  - "完成标准"让 AI 知道何时停手

### 要不要
**必须要**。

### 位置对不对
**第 1 位，对的**。使命必须最先说。✅

## 节 3：[依赖检测]

### 在说啥
"开工前先看有没有这些东西，没有就不干"。

### 好在哪
- **Fail Fast**：没 Spec 直接停，不浪费力气瞎审
- 必需 vs 可选分得清楚

### 差在哪
- **没说怎么检测**：怎么算"代码已存在"？看啥？
- **失败话术没给**：AI 自己编，每次说法不一样

### 咋改 + 为啥改
加"检测方法 + 锁死话术"：

```
- Product-Spec.md：用 Read 检查存在 + 搜索[功能需求]章节
  失败话术（一字不改）："❌ Product-Spec.md 不存在或功能需求为空..."

- 项目代码：Glob 查 package.json/Cargo.toml/go.mod/requirements.txt
  失败话术："❌ 未识别到项目代码..."
```

- **为啥明确检测方法**：不写清楚，AI 可能用 Read、也可能用 Grep、也可能瞎猜 → 结果不稳定
- **为啥锁死话术**：AI 自己编会说"可能没找到"这种软话，用户就忽略了

### 要不要
**必须要**。

### 位置对不对
**建议调到第 3**（退后一位）。
- **原因**：依赖检测是"开工前"的事，但应该让 AI **先读 [第一性原则]**（装好价值观）再读依赖检测。这样检测失败时 AI 会按"不信任声明"给硬话，而不是软话。

## 节 4：[第一性原则] ⭐

### 在说啥
"你做事的底线、价值观、铁律"。这是魂。

### 好在哪
- 每条都具体，不空泛
- 每条都点名反例（"不接受'大致匹配'"）
- 本质是**约束 AI 的语言倾向**（AI 天生爱说"大概"、"基本"，这里明文禁）

### 差在哪
- **"联网优先"和主业弱相关**：code-review 主要是比对 Spec 和代码，用不到 WebSearch。放这里会让 AI 过度联网
- **四条没优先级**：冲突时听谁的？比如"不放过"要求全查 vs 100 条 Spec 太多
- **没边界**：100 条全查不现实，应允许抽样

### 咋改 + 为啥改

```
[第一性原则]（优先级从高到低）

1. 不信任声明（最高）
2. 证据为王
3. 不放过（Spec > 50 条允许模块抽样，但需注明范围）

（删除"联网优先"，下沉到 [审查策略] 作为条件性动作）
```

- **为啥加优先级**：冲突时 AI 有据可依
- **为啥删联网优先**：放第一性原则会被强化，但主业不需要。占坑会挤掉更重要的
- **为啥加抽样条款**：给 AI 一个"极端情况下合理妥协"的路径。没它 AI 要么死磕卡住，要么偷偷跳过（更糟）

### 要不要
**必须要**。

### 位置对不对
**建议前移到第 2**（紧跟 [任务]）。
- **原因**：Prompt 前面的内容权重更高。原则是判断依据，应该在所有具体规则之前就植入。现在放第 4，等 AI 读到时权重已被前 3 节稀释。

## 节 5：[输出风格]

### 在说啥
"你审查完怎么说话"。控制 AI 的语气表达。

### 好在哪
- ✓ / × 清单给 AI 清楚的"禁/许"
- 3 个例子给了可模仿的句式

### 差在哪
- **没限定长度**：Spec 100 条审出来报告会极长
- **缺反例**：只给"该这么写"，没给"不该这么写"
- **没要求数字化总览**：用户应一眼看到"23/30 通过"
- **和节 9 的报告模板风格冲突**：
  - 这里是**行内叙述**（"Spec 要求... 代码中..."）
  - 那里是**分类清单**（"✅ 完整实现（X 项）"）
  - 两套并存，AI 会混用

### 咋改 + 为啥改
把节 5 和节 9 的第五步**合并**为一节 [输出格式]：

```
[输出格式]

每条结论 ≤ 50 字。
报告开头必须有总览：【✅ X  ⚠️ Y  ❌ Z  🔴 W】/ 总 N

分类清单式（不是行内叙述）：
  ✅ 完整实现（X 项）
  - [功能名]：[代码位置] — [验证方式]
  ⚠️ 部分实现（X 项）
  ❌ 未实现（X 项）
  🔴 安全问题（X 项）

反例（明文禁止）：
  × "大部分功能已实现"
  ✓ "23/30 项完整实现"
  × "看起来正常"
  ✓ "已验证 session-list.tsx:89"
```

- **为啥加反例**：看到"不该这么写"的具体句式，比抽象规则更有约束力
- **为啥合并两节**：同一件事写两处会飘，改一处忘另一处
- **为啥要总览**：用户打开第一眼看到数字，比读 30 条描述快 100 倍

### 要不要
**必须要**（合并后）。

### 位置对不对
**建议后移到第 6**。
- **原因**：输出格式是"末端"。前面应先讲"做什么、怎么做"，最后讲"怎么呈现"。现在放第 4 太靠前。

## 节 6：[文件结构]

### 在说啥
"我家就一个文件"。

### 好在哪
- 勉强——明确声明没有其他模板文件

### 差在哪
- **信息量趋零**：一行树图，读者得到的信息 ≈ 0
- **和其他 Skill 风格"强行对齐"**：dev-builder 有多文件所以有意义，code-review 照搬是画蛇添足
- **反而误导**：读者会疑惑"是不是该有别的文件丢了"

### 咋改 + 为啥改
**直接删除**。

- **为啥删**：大模型 prompt 每一个字都是钱、是注意力预算。装饰性内容要零容忍。

### 要不要
**不要。删除**。❌

### 位置对不对
— （被删）

## 节 7：[审查维度清单] ⭐（核心，问题最密集）

### 在说啥
"你具体要查哪几样"。Skill 的核心工作内容。

### 好在哪
- **两阶段分层好**：先对错，再优劣（功能都没做对，挑美丑没意义）
- 安全扫描给了可 grep 的模式，不空谈
- 每个维度列了检查项

### 差在哪（6 个问题）

| # | 问题 | 说明 |
|---|---|---|
| 1 | UI 一致性无容忍度 | `#FF0000 vs #FF0102` 算不算偏离？没标准 |
| 2 | 文件大小 300 行拍脑袋 | TS 合理，JSON/SVG 3000 行也正常，一刀切误报 |
| 3 | 命名规范只覆盖前端 | Python/Go/Rust 惯例完全不一样 |
| 4 | Spec 漂移判定模糊 | "可能是好的扩展，也可能是 scope creep"——可能是啥？ |
| 5 | Stage 1→2 门槛不清 | "HIGH priority 停"，但 HIGH 没定义 |
| 6 | 缺维度 | 性能、可访问性、i18n、可测试性 |

### 咋改 + 为啥改

核心改动：**每个维度加「容忍度/阈值/规则源」**。

```
[UI 一致性] 容忍度表
  颜色：精确匹配（hex 完全相同）
  间距：允许 ±2px
  字号：精确匹配
  超出容忍 → ❌

[代码质量] 文件阈值（按扩展名）
  .ts/.tsx: 300
  .py: 500
  .json/.svg/.sql: 不限

[安全扫描] 规则源（唯一）
  全部写在这里，不再分散到[审查策略]

[Stage 门槛]（明文定义）
  Stage 1 任一条出现 → 不进 Stage 2：
  - ❌ 未实现核心功能
  - ⚠️ 部分实现 ≥ 3 项
```

- **为啥加容忍度**：AI 不是设计师，看到 `#FF0000 vs #FF0102` 没直觉。用数字替代直觉。
- **为啥分语言阈值**：真实项目不都是 TS。一刀切 = 误报 = 信任度下降。
- **为啥锁死 Stage 门槛**：原文说"HIGH 问题停"但 HIGH 没定义 = prompt bug。

### 要不要
**必须要**。

### 位置对不对
**建议前移到第 4**（紧跟依赖检测）。
- **原因**：这是核心工作内容，应该更早暴露给 AI。现在排第 6，被 [文件结构] 这种凑数内容挡路。

- 五步清晰、线性
- 第一步细化了三种审查范围（全量/Phase/Task）

## 节 10：[初始化]

### 在说啥
"开机从哪儿开始跑"。

### 好在哪
- 一行，不会迷路

### 差在哪

**必须要**。

# 💡 学生要带走的三个核心思想

### 1. Prompt 的每个字都在抢 AI 的注意力
- 装饰性内容（[文件结构]）= 浪费预算
- 重复定义（两处安全扫描）= 二次抢位
- 放错位置（[输出风格] 第 4）= 位置权重失衡

### 2. 单一事实源（Single Source of Truth）
- 同一条规则只能在一处定义
- 有冲突时 AI 行为必定飘
- 维护成本随冲突数量指数上升

### 3. 用结构做约束，不是用文字
- 说"要严格" 不如给 "HIGH 的明文判定规则"
- 说"别模糊" 不如给 "容忍度 ±2px" 的数字
- AI 不懂"大概"，只懂"精确"

# 📖 术语速查（碰到专业词回来看）

| 术语 | 意思 |
|---|---|
| Prompt | AI 的输入指令。SKILL.md 本质就是一个大 prompt |
| Fail Fast | 尽早失败。前置条件不满足就停，别往下走 |
| Single Source of Truth | 单一事实源。同一信息只在一处定义 |
| Scope Creep | 范围蔓延。做了 Spec 之外的功能 |
| 注意力权重 | AI 读 prompt 时前面的内容影响力更大 |
| 容忍度 | 允许的偏差范围（如颜色必须精确、间距允许 ±2px）|

# 🧠 理论篇：为啥要这么改？（小白版）

前面讲了"怎么改"。理论篇讲**"为啥"**。用类比讲，不用术语。

---

## 理论 A：为什么 Prompt 顺序这么重要？

### 类比 1：作文开头定基调

你写一篇议论文。第一段是"保护环境很重要"。那后面所有段落，老师都会**按"环保"的角度**来读。

就算你第五段突然写"昨天吃了火锅很好吃"，老师也会努力联想——"是不是在说火锅店浪费食物污染环境？"

**AI 读 prompt 完全一样**。前面看到的内容会**框住**后面所有理解。

### 类比 2：面试前 30 秒

面试官进门先看到你西装笔挺——后面你讲话磕巴，他会觉得"紧张，人挺好"。
进门先看到你穿拖鞋——后面你侃侃而谈，他会觉得"油嘴滑舌，不靠谱"。

**前面的第一印象，权重是后面的好几倍**。

### 对应到 code-review SKILL.md

当前顺序：
```
1. [任务]
2. [依赖检测]
3. [第一性原则]  ← AI 读到这里时，前面 2 节已经占了注意力
4. [输出风格]     ← 这个其实不重要，却占了第 4 位
5. [文件结构]     ← 废话居然还占着位置
6. [审查维度清单] ← 核心内容，结果排第 6
```

**问题**：AI 最该"装好脑子里"的 [第一性原则]，要等读完前 2 节才出现。等出现时，"前面的内容"已经把 AI 的注意力预算用掉了一半。

建议顺序：
```
1. [任务]          ← 你来干啥
2. [第一性原则]    ← 你的底线（权重拉到最高！）
3. [依赖检测]      ← 开工前置
4. [审查维度]      ← 核心内容（早暴露）
5. [工作流程]      ← 主线
6. [输出格式]      ← 末端事
7. [初始化]        ← 入场口
```

### 反面教材：顺序错了会发生啥

**场景**：用户的 Spec 写得模糊，有一条叫"用户能删除会话"但没说是软删还是硬删。

- **当前顺序下**（原则排第 3）：
  AI 读到 [审查维度]（第 6 节）时，前面 5 节已经稀释了原则的影响力。AI 可能"自作主张"：觉得"删除"大概是硬删，代码里有 `DELETE FROM sessions`，**标 ✅ 通过**。
  
- **建议顺序下**（原则排第 2）：
  [不信任声明] 已经植入 AI 脑子。读到歧义条目时，AI 第一反应："Spec 没说清，我不能猜" → **标 ❓ 待澄清**。

**同样的 Spec、同样的代码、不同的顺序，产出不同的结论**。这就是顺序的威力。

### 要不要
**必须要重排**。这不是锦上添花，是 prompt 的基本功。

---

## 理论 B：为什么"同一件事只能写一处"？（单一事实源）

### 类比 1：合同条款

你和客户签合同，第 3 条写"交付日期 2026-04-30"，第 15 条写"交付日期 2026-05-15"。

客户问你：到底哪个算？你没法回答。**两个都说，等于都没说**。

### 类比 2：家里两个钟

客厅挂的钟 8:00，卧室挂的钟 8:03。你问"现在几点？"——永远不知道该信哪个。
唯一的办法是**以一个为准，另一个看齐**。

### 类比 3：Excel 表格

你维护一个客户列表。张三的手机号在 A 表里是 `13800138000`，在 B 表里是 `13811112222`。
下次有人打电话问你"张三的手机号"，你说哪个？
**结论：只能有一个表是真的，另一个要么删除要么同步**。

### 对应到 code-review SKILL.md

当前的"两处定义"问题：

| 规则 | 第一次出现 | 第二次出现 | 一致吗？ |
|---|---|---|---|
| 安全扫描清单 | 节 7 [安全扫描] | 节 8 [安全扫描法] | ❌ **不一致**（节 7 有 SQL 注入，节 8 没有；节 8 有 AI Key，节 7 没有） |
| 逐项对照方法 | 节 7 [功能完整性] | 节 8 [逐项对照法] | ❌ 一个讲 What，一个讲 How |
| UI 对比方法 | 节 7 [UI 一致性] | 节 8 [设计数值对比法] | ❌ 重复 |
| "第一步"入口 | 节 3 [依赖检测] | 节 10 [初始化] | ❌ **都自称"第一步"** |

### 这会导致什么后果？

**后果 1：维护噩梦**
半年后你想加一条"检测硬编码 S3 密钥"。你改了节 7。没改节 8。
AI 每次审查随机使用其中一个清单——**有时候能查出，有时候查不出**。你以为自己加了规则，其实时有时无。

**后果 2：AI 行为飘**
AI 读到两处矛盾时，不会报错，它会"选一个"。但选哪个是随机的（基于上下文）。
**同一个项目审查两次，结果可能不同**。用户丧失信任。

**后果 3：改 Skill 的成本指数上升**
- 1 处重复 → 改规则要找 2 个地方
- 2 处重复 → 改规则要找 4 个地方
- 3 处重复 → 8 个地方
- 你很快就改不动了，只能放弃 Skill

### 在软件工程里这叫什么？

**DRY 原则**：Don't Repeat Yourself。
一条真理、一个规则、一段代码——**只能存在一个地方**。其他地方要用就引用这里，不能复制。

### 要不要
**必须做到**。这是 Skill 能长期演化的基础。

## 理论 C：改前 vs 改后 —— 实际会发生什么？

- 项目：一个待办事项 App
- Spec 有 15 条功能需求
- 项目用的是 **Python 后端 + React 前端**
- 设计稿颜色 `#4A90E2`，代码里写的是 `#4B91E3`（差 1）

读完 [第一性原则]           → 被"不放过"打动，但"联网优先"让它有点飘

读完 [文件结构]             → ???这是啥，算了跳过

**Step 2 - 跑到 [第四步：代码质量] 的 `tsc --noEmit`**
```
$ tsc --noEmit

```
**AI 懵了**。因为项目是 Python，没装 TypeScript。
原文没说"怎么办"——AI 可能：
- 选项 A：直接跳过这步，报告里不提
- 选项 B：报错中止
- 选项 C：尝试 `mypy`（但也不一定装了）

**Step 3 - 检查颜色 `#4A90E2 vs #4B91E3`**

**同一个代码两次审查结论不同**。

**Step 4 - 安全扫描**

- 用节 7 → 漏查 AI Key

**总有漏网之鱼**。

**Step 5 - 输出报告**
原文节 5 是行内叙述风格，节 9 是分类清单风格。AI 混用：

⚠️ 部分实现（2 项）
- ...
```
**格式混乱，用户体验差**。

### 场景推演 2：改后 AI 怎么走

**Step 1 - AI 读 SKILL.md**

读完 [任务]                 → 知道使命 + 不做清单 + 完成标准
读完 [第一性原则]           → 三条铁律植入，权重高

读完 [工作流程]             → 主线清晰，含异常处理
读完 [输出格式]             → 统一模板 + 反例

```

**Step 2 - 识别语言**

只有一处规则源（7 条模式）。AI 一条条执行：

Priority 分级
🔴 High: 1（安全）

**格式稳定、数字清楚、证据齐全**。用户扫一眼就知道项目健康度。

## 🎓 三个理论的学习重点（带走这三句话）

### 句 1：**位置就是权重**
Prompt 里的顺序不是可随便调的装饰。前面的内容会框住后面的理解。
**把最重要的原则放在最前面**。

### 句 2：**重复就是 Bug**
同一条规则写两遍，不是"双保险"，是"双隐患"。
**维护成本随重复数量指数上升**。

### 句 3：**规则要比人更刻板**
AI 不懂"大概"、"看起来"。
**用数字、用容忍度、用规则源取代所有主观判断**。

## 📚 延伸：如果你想自己改进其他 Skill

按这个顺序体检：

**第一遍：找重复**
- 同一条规则是否出现在多个章节？
- 如果有，合并到一处，其他地方只引用。

**第二遍：找冲突**
- 是否有两处都自称"第一步"/"默认"/"最高优先级"？
- 如果有，明确一个为主，另一个说"见 X 节"。

**第三遍：查顺序**
- 原则是否在前 3 节？
- 核心工作内容是否在前 5 节？
- 输出格式是否在后半段？

**第四遍：查具体性**
- 所有阈值是否有数字？（不是"大"、"多"、"快"）
- 所有规则是否有判定条件？（不是"可能是"、"可以是"）

**第五遍：查可移植性**
- 是否硬编码了某种语言/工具？
- 能否动态识别？

这五遍过完，Skill 基本上就合格了。

# 🔬 深挖篇：三个核心节的底层逻辑

前面讲了"怎么改"和"为啥改"。深挖篇讲**每个决策背后的原理**。
读完这部分，你改任何 Skill 都能自己判断对错。

---

# 深挖 1：[第一性原则] 的每条铁律背后是什么？

原则不是凭空写的。每条都在**对抗 AI 的某种天生倾向**。
如果不知道"在对抗什么"，你写原则就只是抄别人。

## 铁律 1：不信任声明

### 对抗的 AI 本能：**讨好本能**

AI 在训练时被告知"要有帮助"。这让它有个毛病——**倾向于给肯定答复**。

**类比**：推销员
- 你问推销员"这产品好吗"
- 他本能回答"好"
- 这不是恶意，是他的工作天性
- 要让他说实话，只能**用合同条款约束**："若夸大宣传赔偿 X 万"

**AI 同理**：
- 用户问"代码写对了吗"
- AI 本能"写对了，看起来都实现了"
- 你必须明文禁止："不接受'看起来'、'大致'这种词"
- 否则 AI 的讨好本能就占上风

### 为什么这条要放第一？

因为**所有后面的规则都建立在"AI 敢说实话"之上**。如果 AI 连实话都不敢说，再多的维度清单也没用——它会每项都标 ✅。

### 实战对比

**没这条时 AI 的典型回答**：
> "我审查了代码，**大部分功能都已实现**，**整体看起来符合 Spec**。"

**有这条时 AI 被迫说**：
> "Spec 第 1.1 条'用户登录'：代码中 auth.py:45 有 login 函数 ✅
> Spec 第 1.2 条'记住密码'：**未找到对应实现** ❌
> Spec 第 2.3 条'邮箱验证'：EmailVerify 组件存在但 API 端点缺失 ⚠️"

同一段代码，两种天差地别的结论。

---

## 铁律 2：证据为王

### 对抗的 AI 本能：**幻觉本能**

LLM 有个已知问题——**会产生"看起来合理"但根本没发生过的引用**。

**真实案例**：
- AI 说："login 函数在 auth.py 第 45 行"
- 你打开一看，第 45 行是一条注释
- 真正的 login 函数在第 78 行

这不是 AI 说谎，是它的**模式匹配失效**——凭感觉说出"45 行"这个数字。

### 为什么"要附证据"能治这个病？

**类比**：学生写历史论文
- 不要求出处 → 学生可能瞎编"某教授说过..."
- 要求附出处 → 学生被迫**真的去查书**

**AI 同理**：
- 不要求证据 → AI 凭感觉说"代码在某处"
- 要求附 "文件:行号 + 验证方式" → AI 被迫**真的去 Read 代码**

### "证据" 具体指什么？

| 结论 | 合格证据 | 不合格 |
|---|---|---|
| ✅ 完整实现 | 文件:行号 + 函数名 + 预期行为验证 | "已实现" |
| ⚠️ 部分实现 | Spec 原文 + 代码位置 + 缺失内容 | "部分完成" |
| ❌ 未实现 | Spec 原文 + 搜索范围（证明真的找过） | "未找到" |
| 🔴 安全 | 文件:行号 + 匹配的危险模式 | "有风险" |

### 为什么要到"行号级别"？

因为只有行号是**可验证的**。
用户想核对 → 点开文件跳过去一看 → 立马知道 AI 说得对不对。

**这叫"可证伪性"**——好的结论必须是能被证明是错的。只有可证伪，才能建立信任。

---

## 铁律 3：不放过

### 对抗的 AI 本能：**总结本能**

LLM 的训练目标之一是"总结长文本"。这让它超擅长说：
- "大部分功能已实现"
- "整体架构合理"
- "主要流程畅通"

**但审查场景恰恰相反**——要的是**逐条核对**，不是概括。

### 类比：体检报告

- 不合格的体检报告："各项指标大体正常"
- 合格的体检报告：
  ```
  血压：128/85     ✅ 正常
  血糖：5.6        ✅ 正常
  胆固醇：6.8      ⚠️ 偏高（正常值 <5.2）
  ```

**AI 天生想写第一种**，你必须强迫它写第二种。

### "不放过" 怎么落地？

**技术层面**：
- 先把 Spec 每条功能**编号**（1.1、1.2、2.1……）
- 报告里每个编号都必须出现
- 不出现 = 遗漏 = 不合格

**心理层面**：
- 告诉 AI "**绝不允许说'其余功能看起来正常'**"
- 点名具体的反面句式

### 为什么要允许抽样？

但"不放过"碰到 100 条 Spec 就崩了。实际成本不允许。

**改进方案**：给 AI 一个**合理妥协路径**
```
若 Spec > 50 条 → 允许按模块抽样，但必须：
1. 在报告开头写"本次抽样范围：X 模块（占 60%）"
2. 被抽到的模块内所有条目仍然不放过
```

**精髓**：
- 硬性规则（不放过）+ 软性 buffer（超量允许抽样）
- 不给 buffer → AI 要么死磕要么偷偷跳过（更糟）
- 给了 buffer → AI 可以"明面上合理妥协"

---

## 铁律 4：联网优先（**为啥要删**）

### 这条错在哪？

**错位：把工具当价值观**
- 联网是"**认知扩展工具**"（遇到陌生东西去查）
- 不是"**价值观/判断依据**"（做事的底线）
- 把工具当价值观，相当于把"百度"当成"你的做人原则"

### 对比其他三条

| 铁律 | 是啥 | 用处 |
|---|---|---|
| 不信任声明 | 判断依据 | 所有结论都遵循 |
| 证据为王 | 判断依据 | 所有结论都遵循 |
| 不放过 | 判断依据 | 所有条目都遵循 |
| 联网优先 | 工具偏好 | 只有少数场景用得上 |

**前三条是"无条件原则"，第四条是"条件性动作"**——不是一个层级。

### 强行保留会怎样？

AI 会**过度联网**：
- 审查时看到 `eval(` → 联网搜 "JavaScript eval security"
- 看到 `innerHTML` → 再搜一次
- 看到陌生库 → 又搜
- 100 条 Spec 能触发 30+ 次 WebSearch

**时间和 token 成本爆炸**，审查效率归零。

### 怎么改？

**下沉到 [审查策略] 作为条件性动作**：
```
[条件性联网]
仅当：
- Grep 命中未见过的危险模式（不在规则源清单里）
- 用户问到某个新 CVE
→ 执行 WebSearch
其他情况：按内置规则判，不联网
```

---

## 第一性原则为什么必须排第 2？

### 用"装系统"来理解

**类比：买新手机**

步骤：
1. 开机（= [任务]：告诉它你要用这手机）
2. **设置隐私/账号/基础偏好**（= [第一性原则]：基础人设）
3. 连网（= [依赖检测]）
4. 装 App（= [审查维度] 等具体工作）
5. 用 App（= [工作流程]）

**你能跳过第 2 步直接装 App 吗？**
能，但每个 App 都会问一遍"是否允许通知"、"是否读取通讯录"、"是否定位"——你会被骚扰疯。

**AI 同理**。如果不先在第 2 步植入"原则"，每个维度都要重新告诉 AI "要严格、要有证据、要不放过"。

**原则一旦装好，后面所有维度自动遵循**。这就是排第 2 的意义。

# 深挖 2：[审查维度清单] 六大问题逐个拆

## 问题 1：UI 容忍度为啥必须是"精确 hex 匹配"？

### AI 的盲区

AI 不懂"**品牌一致性**"。
对 AI 来说 `#4A90E2` 和 `#4B91E3` 都是"蓝色"。
对设计师来说：
- `#4A90E2` = 品牌主色
- `#4B91E3` = 乱写的数值，破坏品牌一致性

### 为什么不能"差不多就行"？

**反例**：字节跳动品牌色是 `#FE2C55`。
如果允许 ±1，代码里可能写成：
- `#FE2C55` → 品牌主色
- `#FF2D56` → 偏差 1
- `#FD2B54` → 又偏差 1
- ...

**一个项目里蓝色有 5 种色值**，全都"接近"。用户看不出差异，但品牌整体质感崩塌。

### 间距为啥允许 ±2px？

**因为有物理原因**：
- 浏览器 subpixel rendering（亚像素渲染）会偏差
- 不同 DPI 屏幕可能有 1-2px 误差
- 这是**客观不可避免的**

**颜色不同**：颜色没有物理误差，代码写什么就渲染什么。**没理由允许偏差**。

### 规则的本质：分清"人为偏差" vs "物理偏差"

- **人为偏差**（颜色、字号、圆角）→ 零容忍
- **物理偏差**（间距、抗锯齿）→ 给合理 buffer

---

## 问题 2：文件大小阈值为啥是 300？

### 这不是绝对标准

**业界经验值**：
- 超过 300 行的文件，**90% 在做多件事**
- 看 Google、Facebook、微软的 Lint 规则，阈值都在 200-500 之间
- 300 是中位数，兼顾严格和宽容

### 但不能一刀切

**反例 1**：迁移脚本
```sql
-- database/migrations/001_init.sql
-- 初始化 50 张表，3000 行 CREATE TABLE
```
这个文件**理应很长**。拆开反而乱。

**反例 2**：配置文件
```json
// i18n/zh-CN.json
// 10000 条翻译
```
越长越好。

### 正确做法：按扩展名分阈值

```
.ts/.tsx/.js/.jsx: 300    （业务逻辑应该拆）
.py:               500    （Python 喜欢模块化）
.go:               500    （Go 习惯长文件）
.rs:               500    
.java:             500    （类体大）
.json/.yaml:       不限   （数据文件）
.sql:              不限   （DDL 脚本）
.svg:              不限   （矢量图）
.css/.scss:        1000   （样式可长）
```

### 阈值不是规则，是"信号"

**记住**：超过阈值不等于"错"，而是"**警告需要人工复核**"。
- 300 行 TS 文件 → AI 标注 "⚠️ 超大文件，请核对职责"
- 不是 ❌ 直接判错

## 问题 3：命名规范为啥不能统一？

### 因为"惯例" 是历史形成的，不是好坏问题

**Python**：
- `snake_case` 是 **PEP 8 官方规定**
- Python 社区 20 年都这么写
- 你强行用 `camelCase` = 你不是 Pythonic → 别人看到觉得你不专业

**Go**：
- 大小写决定**可见性**（不是风格！）
- `Login()` 是公开 API
- `login()` 是包内私有
- 你改个大小写 = 编译都不一样

**Rust**：
- 结构体 `PascalCase`
- 函数 `snake_case`
- 模块 `snake_case`
- 常量 `SCREAMING_SNAKE_CASE`
- 五种风格共存——每种都有语义

### 如果 SKILL.md 强行"统一规范"会怎样？

**场景**：用户项目是 Python。
AI 读到规则："camelCase 函数"。
它要么：
- A：按 JS 规则判 Python 代码错（误报一片）
- B：识别到是 Python 就忽略这条（规则失效）

**B 情况下规则写了等于没写**。还不如一开始就按语言分。

### 正确做法

```
[命名规范表]

TypeScript / JavaScript:
  组件: PascalCase
  函数/变量: camelCase  
  文件: kebab-case
  常量: UPPER_SNAKE_CASE

Python:
  类: PascalCase
  函数/变量/文件: snake_case
  常量: UPPER_SNAKE_CASE

Go:
  导出标识符: PascalCase
  包内标识符: camelCase
  文件: snake_case
  常量: PascalCase 或 UPPER_SNAKE_CASE

Rust:
  结构体/枚举/Trait: PascalCase
  函数/变量/模块: snake_case
  常量: UPPER_SNAKE_CASE
```

## 问题 4：Spec 漂移怎么判 🟢 vs 🔴？

### 当前原文的问题

原文写："⚡ 可能是好的扩展，也可能是 scope creep"——**"可能是啥"是废话**。

AI 读完不知道怎么判，只能随便给个 ⚡ 拉倒。

### 判定依据：**"用户可见面"测试**

问一个问题：**用户打开 App，能看见这个功能吗？**

| 答案 | 归类 | 颜色 |
|---|---|---|
| 看不见（基础设施） | 🟢 合理扩展 | 可保留 |
| 看得见（新功能） | 🔴 Scope Creep | 必须回 Spec 讨论 |

### 实例

**🟢 合理扩展（看不见）**：
- 日志系统（logger.py）
- 错误边界（ErrorBoundary.tsx）
- 缓存层（cache.ts）
- 数据库连接池
- CI/CD 配置

→ 这些支撑功能运行，但用户不直接看到。

**🔴 Scope Creep（看得见）**：
- Spec 没写"用户登录"，代码里做了
- Spec 没写"分享到微信"，代码里做了
- Spec 没写"订阅付费"，代码里做了
- Spec 没写"深色模式"，代码里做了

→ 用户会在界面上看到这些，引入了新的"用户可感知功能面"。

### 为什么 Scope Creep 是红色？

- 可能是开发者"好心办坏事"（多加了 Spec 没要的功能）
- 但对项目来说：
  - 偏离范围 → 交付不可控
  - 引入未讨论的 UX → 可能和产品定位冲突
  - 增加维护成本 → 后续 bug 多一个来源
- 必须回到产品讨论："这个真的要加吗？"

---

## 问题 5：Stage 门槛为啥这样定？

### 核心逻辑：先对错，再优劣

**类比**：开车考试
- 科目 1（理论）没过 → 不能考科目 2（实操）
- 为什么？因为连交规都不懂，上路是危险的

**审查同理**：
- Stage 1（功能）没做对 → 查 Stage 2（代码质量）没意义
- 功能都没实现，纠结代码缩进干啥？

### "未实现核心功能" 为啥直接阻塞？

**类比**：盖房子
- 工期审查发现"墙没砌完"
- 还审查"墙砖颜色是否一致"吗？不，先砌墙
- 墙砌完了，再说墙砖美观问题

**核心功能 = 墙**。墙没砌就审美丑 = 浪费时间。

### "部分实现 ≥ 3 项" 的 3 是怎么来的？

**经验数据**：
- 1 项有问题 → 可能是小疏漏
- 2 项有问题 → 可能是特定模块没做完
- **3 项以上 → 整体成熟度不够**，不适合继续细审

这个 3 不是绝对的。可以根据项目大小调整：
- 小项目（Spec < 20 条）→ 3 条
- 中项目（Spec 20-50 条）→ 5 条
- 大项目（Spec > 50 条）→ 10 条

### 但阻塞要不要有"例外条款"？

**好问题**。有例外：
- 如果"未实现" 和"部分实现" 都是**同一个模块**——说明是模块问题，不影响其他模块的 Stage 2
- 这种情况可以**降级阻塞为警告**，其他模块继续审

## 问题 6：漏掉的维度为啥必须补？

### 缺的四个维度

**性能**
- 真实案例：某电商前端没查 N+1，上线后商品列表页每打开加载 100 次 API
- 成本：用户流失 + 服务器账单暴涨
- 审查成本：grep `useEffect` 看依赖数组，5 分钟搞定
- **不查 = 小问题变大事故**

**可访问性 (a11y)**
- 真实案例：某 SaaS 没做键盘导航，无障碍测试不过关
- **后果：欧盟 WCAG 合规罚款、美国加州 ADA 诉讼**
- 这不是"锦上添花"，是"**合规红线**"
- 查的东西：alt、aria-label、语义标签、对比度

**国际化 (i18n)**
- 真实案例：产品要打入日本市场，代码里硬编码了 500 处中文
- 改造成本：3 个月工作量
- 提前查：`Grep "[\u4e00-\u9fa5]+"` 就能找出硬编码中文
- **提前 5 分钟 vs 后期 3 个月**

**可测试性**
- 项目没有单元测试 → 每次改动都是"赌博"
- 查：项目是否有 `test/` 或 `spec/` 目录
- 有但覆盖率低 → 🟡 警告
- 完全没有 → 🔴（对任何严肃项目）

### 这些维度为啥一开始没写？

**很可能是"起步简单"的考虑**——先覆盖基础维度，后续迭代补。
但一旦这个 Skill 被用来审真实项目，这些维度**就是刚需**。

# 深挖 3：[工作流程] 的四个缺陷如何补

## 缺陷 1：异常恢复怎么做？

### 三种异常 + 对应处理

### 异常 A：Spec 歧义

**场景**：Spec 说"用户能删除任务"，但没说：
- 软删除（标记为已删）还是硬删除（从数据库删）？
- 删除后能恢复吗？
- 批量删除支持吗？

### 为什么 AI 不能自己澄清？

AI 倾向"按最常见解读"走，会把"删除"默认理解为"硬删除"。
但如果用户本意是"软删除可恢复"——**AI 的猜测和真实需求南辕北辙**。

### 正确做法：**标 ❓ 不猜**

```
审查发现 Spec 歧义 → 生成结论：
  ❓ 待澄清 - 功能 1.3 "用户能删除任务"
    歧义点：是软删除还是硬删除？
    代码现状：硬删除（DELETE FROM tasks WHERE id = ?）
    建议：和产品确认后再判定

→ 报告末尾单列"待澄清"章节
```

### 为啥这比"猜"好？

- 猜对 → 浪费时间（用户还是要确认）
- 猜错 → 结论完全错 → 比漏审更糟
- 标 ❓ → 明确暴露 → 用户一眼就知道要做什么

---

### 异常 B：编译失败

**场景**：执行 `$TYPECHECK_CMD` 返回 20 个类型错误。

### 处理原则：**记但不阻塞**

- 编译问题 ≠ Spec 不满足
- 这是**两个独立维度**
- 不能因为编译错就停止其他维度的审查

### 实现方式

```
[第四步] 代码质量 + 安全
  执行 $TYPECHECK_CMD
  若失败：
    - 记 🔴 编译错误：[错误摘要]
    - 继续审查其他维度
  若成功：
    - 记 ✅ 编译通过
    - 继续
```

### 为啥不先修编译再审？

- 用户可能想要**完整的审查视角**
- 编译错可能只是临时的（比如正在开发中）
- 一次性看完所有问题，比修完编译再审更高效

---

### 异常 C：工具不可用

**场景**：Spec 说有设计稿，但设计工具 MCP 没连上。

### 处理：**降级 + 明文标注**

```
审查 [UI 一致性] 时发现设计工具 MCP 未连接：
  → 降级：标注"此维度未执行：设计工具 MCP 未连接"
  → 不假装审查了（这是欺骗）
  → 不标 ✅（没证据）
  → 不标 ❌（不是代码错）
  → 使用独立标记：⏭ 跳过
```

### 为啥不能静默跳过？

用户看报告时会以为所有维度都审了。
静默跳过 = **假报告** = 信任崩塌。

## 缺陷 2：Priority 同步打标怎么实现？

### 当前原文的问题

节 9 把 Priority 放在报告末尾作为"**汇总**"。
但 AI 生成每条结论时并不知道该条属于什么级别——只能**最后再判一遍**。

### 类比：工厂流水线

**不好的工序**：
- 组装 → 装箱 → 装箱完再统一打标签（已经装箱了，标签贴错了要拆）
- 累、易错

**好的工序**：
- 组装 → 贴标签 → 装箱（每个零件做完就贴，不积压）

### 改进方案：**每个维度下挂 Priority 规则表**

```
[功能完整性]
  Priority 规则：
  - ❌ 未实现核心功能 → 🔴 High
  - ❌ 未实现辅助功能 → 🟡 Medium
  - ⚠️ 部分实现核心 → 🔴 High
  - ⚠️ 部分实现辅助 → 🟡 Medium
  - ✅ 完整实现 → 不打标

[UI 一致性]
  Priority 规则：
  - 颜色/字号超容忍 → 🟡 Medium
  - 布局超容忍 → 🟡 Medium
  - 交互状态缺失 → 🔴 High

[安全扫描]
  Priority 规则：
  - 硬编码凭据/API Key → 🔴 High（无条件）
  - eval/XSS → 🔴 High
  - 路径泄露（非凭据）→ 🟡 Medium
  - 依赖漏洞 → 取决于 CVE 严重度

[Spec 漂移]
  Priority 规则：
  - Scope Creep → 🔴 High
  - 合理扩展 → 🟢 Low（只记录）
```

### 为什么这样更好？

- AI 生成每条结论时**已经知道级别**
- 末尾汇总只是数数，不再重判
- **减少一次遍历 = 减少一次出错机会**

## 缺陷 3：跨语言识别怎么写？

### 原文的硬编码问题

`tsc --noEmit` 只对 TypeScript 有用。

### 正确实现：**语言识别规则**

```
[第一步] 识别项目语言（新增）

按文件存在性判断，优先级从上到下：

1. package.json 存在
   1a. tsconfig.json 存在 → TypeScript
       $TYPECHECK = "npx tsc --noEmit"
       $LINT = "npx eslint ."
   1b. 否则 → JavaScript
       $TYPECHECK = "echo '(JS 无强类型检查)'"
       $LINT = "npx eslint ."

2. Cargo.toml 存在 → Rust
   $TYPECHECK = "cargo check"
   $LINT = "cargo clippy"

3. go.mod 存在 → Go
   $TYPECHECK = "go build ./..."
   $LINT = "go vet ./..."

4. pyproject.toml / requirements.txt 存在 → Python
   $TYPECHECK = "mypy ."  （若 mypy 未装则跳过）
   $LINT = "ruff check ."  （若 ruff 未装则 flake8）

5. Gemfile 存在 → Ruby
   $TYPECHECK = "（Ruby 无强类型，跳过）"
   $LINT = "rubocop"

6. composer.json 存在 → PHP
   ...

7. 都不匹配 → 未知项目
   $TYPECHECK = "echo skip"
   $LINT = "echo skip"
   同时在报告开头警告："⚠️ 项目语言未识别，跳过编译检查"
```

### 用"动态变量"的好处

- 工作流里统一写 `$TYPECHECK` 和 `$LINT`
- 不管是什么项目，同一个流程能跑
- 未来加新语言只改识别规则，不改流程

### 类比：电源插头

- 当前 SKILL.md：只接美标插头（TS）
- 改后：万能转接头（识别各种插头）

## 缺陷 4：代码地图是啥？

### 当前原文的问题

第二步说"建立代码地图（什么功能在哪些文件里）"——**格式没定义，存哪没说，下游怎么用没说**。

### 改进：**明文定义格式**

```
[代码地图格式]（第二步产出）

Markdown 表格：

| # | Spec 条目 | 涉及文件 | 关键函数/组件 | 备注 |
|---|---|---|---|---|
| 1.1 | 用户登录 | auth/login.py, components/LoginForm.tsx | login(), handleSubmit() | 使用 JWT |
| 1.2 | 用户注销 | auth/logout.py, Header.tsx | logout() | - |
| 2.1 | 创建任务 | api/tasks.py, CreateTaskDialog.tsx | createTask() | 使用 Redux |
| 2.2 | 编辑任务 | api/tasks.py, EditTaskDialog.tsx | updateTask() | 乐观更新 |
...

补充（不在 Spec 里的文件）：
| 文件 | 推测用途 |
|---|---|
| utils/logger.py | 日志 - 合理扩展 |
| components/LoginBonus.tsx | 登录奖励？未在 Spec 出现 - ⚠️ Scope Creep 嫌疑 |
```

### 代码地图的三大作用

**作用 1：逐项比对的基础**
- 第三步审查时不用重新搜索
- 直接按地图跳转到对应文件

**作用 2：报告附录**
- 用户看报告时能快速跳转代码
- 报告自包含，不依赖用户去理解代码结构

**作用 3：Spec 漂移的天然探测器**
- Spec 里没有的条目 → 代码地图的"补充"区
- 自动暴露嫌疑 Scope Creep

### 没有代码地图会怎样？

- 第三步审查时反复搜索同一个文件
- 报告里说"auth.py:45"，用户得自己去找
- Spec 漂移全靠 AI 主动发现（不可靠）

**代码地图 = 审查的骨架**。

# 🎯 深挖篇总结：带走三个底层原理

## 原理 A：**规则是用来对抗 AI 本能的**

不是教 AI 做什么，是**告诉 AI 不要做什么**。
AI 的三大危险本能：
- **讨好**：倾向于肯定答复 → 用"不信任声明"对抗
- **幻觉**：凭感觉编细节 → 用"证据为王"对抗
- **总结**：喜欢概括 → 用"不放过"对抗

看任何 Skill，都问：**它在对抗什么 AI 本能？**
如果说不出对抗什么，这条规则就是空的。

---

## 原理 B：**规则要有"例外条款"**

硬性规则 + 软性 buffer = 健康的规则。

例：
- "不放过" + "超 50 条允许抽样" = AI 不会死磕
- "编译必须过" + "失败不阻塞" = 审查能继续
- "统一规范" + "按语言分" = 规则能落地

**没 buffer 的规则要么被硬撞，要么被偷偷跳过**。都是坏结局。

---

## 原理 C：**工具要可移植、格式要统一**

- 跨语言：不写死 `tsc`，用 `$TYPECHECK` 变量
- 跨工具：MCP 没连？降级 + 明标
- 跨平台：规则用文件扩展名判语言，不用"看看有没有 node_modules"

**可移植性 = Skill 的生命力**。
只能用于 TS 项目的 Skill，用 3 次就被删了。
能用于所有主流语言的 Skill，永远在工具箱里。

# 💬 答疑篇：四个根本问题

## 问题 1：Spec 是什么？

### 一句话答
Spec = `Product-Spec.md`，**项目的需求文档**。

### 它从哪来？
由 `product-spec-builder` 这个 Skill 生成。
通过和用户对话，搞清楚要做什么产品 → 输出结构化 Markdown 文档。

### 它里面装了什么？
- 产品定位（这是啥产品）
- **功能需求**（用户能做什么）← code-review 主要对照这部分
- 用户故事（具体使用场景）
- UI 描述（界面长啥样）
- 非功能需求（性能、安全等）

### 它的作用？
是审查的 **标准答案**。

### 为什么 code-review 离不开它？

**类比**：改作业
- 没标准答案 → 老师怎么改？
- 凭感觉？学生 A 蒙对给 ✅，学生 B 算对但写法不同给 ❌
- 审查变成主观判断 → 没意义

**没 Spec 的 code-review** 会发生什么：
- 标 ✅ 凭啥？凭"代码看起来对"
- 标 ❌ 凭啥？凭"AI 觉得不对"
- 全靠 AI 主观感觉 → 不可信

**更糟糕的场景**：AI 看到没 Spec，会**从代码反推一个"假 Spec"**，然后用假 Spec 审代码 —— **等于自己出题自己答，永远 100 分**。

所以 Spec 是 code-review 工作的 **前提**，不是装饰。

---

## 问题 2：[任务与边界] 和 description 是否类似？

### 一句话答
**长得像，作用完全不同**。一个对外，一个对内。

### 对照表

| 维度       | description（frontmatter）       | [任务与边界]（节内容）              |
|------------|----------------------------------|------------------------------------|
| **给谁看** | 主 Agent 的路由系统              | 被调用起来后的 code-review 自己    |
| **何时读** | 用户每次说话时（路由判断）       | 这个 Skill 被启动后                |
| **长度**   | 一句话                           | 详细清单                           |
| **目的**   | "什么时候叫我"                   | "叫我之后我干嘛、不干嘛、干到啥程度" |

### 类比

- **description = 招聘启事**
  「招高级 QA，做代码审查」
  → 决定老板（主 Agent）会不会找你

- **[任务与边界] = 入职合同**
  「你的职责是 X，你不能做 Y，做完算 Z」
  → 决定你来了之后该做什么

### 实例对比

**description 实际作用**：
> 用户说："帮我审一下代码"
> 主 Agent 扫所有 Skill 的 description → 看到 code-review 写"当用户说要审查代码..."
> → 主 Agent 决定："这事儿叫 code-review"
> → 调起 code-review

**[任务与边界] 实际作用**：
> code-review 被调起来了
> → 第一件事读 [任务与边界]
> → "哦，我要做的是 A B C，不能做 D，完成标准是 E"
> → 按这个去执行

### 为什么必须分两个？

**只有 description**：
- 主 Agent 知道何时叫你
- 但你来了之后不知道做什么 → 自由发挥 → 飘

**只有 [任务与边界]**：
- 你知道做什么
- 但主 Agent 不知道何时叫你 → 你永远不会被启动

两个**配对使用**才能让 Skill 工作。

---

## 问题 2.5：任务 = 审查维度吗？

**不等于**。这是两个层次的东西，绝对不能混淆。

### 对照表

| 概念       | 是什么            | 例子                                     |
|------------|-------------------|------------------------------------------|
| **任务**   | 使命（为什么做）  | "对照 Spec 输出审查报告"                  |
| **审查维度** | 动作（具体查什么）| "查功能完整性、查 UI、查代码质量..."     |

### 类比：医生

- **任务（使命）**：诊断病人健康状况，输出诊断报告
- **维度（动作）**：听诊、量血压、抽血、X 光、问诊...

医生上班不能只知道动作不知道使命：
- "我会量血压、会抽血——但我为什么要做这些？"

医生上班也不能只知道使命不知道动作：
- "我要诊断病人——但具体怎么动手？？"

**两者必须都有**。

### 关系

- **任务 = What & Why**（要做什么、为什么做）
- **维度 = How**（具体怎么做）

任务在前，给方向；维度在后，给手段。

---

## 问题 3：既然维度有具体标准，第一性原则的意义？

### 这是最关键的问题

很多人会觉得："维度都列得这么细了，再写原则不是废话吗？"

**完全相反**。维度和原则解决的是不同问题。

### 本质差别

| 概念       | 解决的问题       |
|------------|-----------------|
| **维度**   | 查 **什么**     |
| **原则**   | 怎么 **思考、表达** |

### 类比 1：法官

- **维度** = 法律条文（具体罪名、量刑标准）
- **原则** = "无罪推定"、"疑罪从无"

法律条文很全了，为啥还需要原则？
- 条文是有限的，原则是无限的
- 遇到条文没规定的情况 → 原则兜底
- 同样的条文，按不同原则解读 → 出不同判决

### 类比 2：医生

- **维度** = 检查项（量血压、抽血、X 光）
- **原则** = "不伤害病人"、"知情同意"

检查项告诉医生"做什么"，原则告诉医生"做的时候怎么权衡"。
比如让你做 X 光，原则让你"权衡辐射风险"。

### 具体到 code-review

**只有维度，没有原则**会出三种问题：

#### 场景 A：维度说"查 SQL 注入"，AI 不能 100% 确定是不是注入
- 没原则 → AI 倾向标 ✅（讨好本能）
- 有"不信任声明" → AI 必须标 ⚠️ 或 ❓，**不能猜**

#### 场景 B：维度说"查 alt 属性"，AI 发现 100 个图里 1 个没 alt
- 没原则 → AI 写"几乎都有 alt"（总结本能）
- 有"证据为王" → AI 必须写"99/100 有 alt，缺失 1 处：banner.tsx:23"

#### 场景 C：维度清单里没列的奇怪代码
- 没原则 → AI 不知道该不该报，可能跳过
- 有"不放过" → AI 知道要报，归到"⚡ 额外发现"

### 第一性原则的三大不可替代作用

**作用 1：约束 AI 的语言倾向**
- 维度管不了 AI 怎么说话
- 原则管："不接受'大致'、'看起来'这种词"

**作用 2：维度清单的兜底**
- 维度永远不可能 100% 覆盖所有场景
- 遇到清单外的事 → 原则给出"判断准则"

**作用 3：跨维度的共性约束**
- 维度是分散的（功能、UI、安全各管一摊）
- 原则是统一的（无论查什么，都要不信任声明、证据为王、不放过）

### 一句话总结

> **维度是"查什么"，原则是"怎么查、怎么说"。**
> **维度是手脚，原则是脑子。** 缺一不可。

## 问题 4：依赖检测的意义？

### 一句话答
**防止 AI 在前置条件不满足的情况下硬干**。

### 表面看 vs 深层看

**表面看**：不就是检查文件存在吗？AI 自己读不就行了？

**深层看**：依赖检测有 4 个不可替代的作用。

### 意义 1：防止"瞎审查"

没有 Spec → 审查的标准是什么？
- 标 ✅ 凭啥？标 ❌ 凭啥？全凭主观
- **没标准 = 没意义**

依赖检测先卡一道："没 Spec 不审"。
**用户被强制去 /product-spec-builder 先生成 Spec**，然后回头审。

### 意义 2：防止 AI 自己编 Spec（最危险）

**如果不卡依赖检测**会发生什么：
- AI 看到没 Spec
- AI 心想："那我从代码反推一个 Spec 吧"
- AI 用反推的 Spec 去审代码
- → **永远全过** ✅✅✅

这叫"**自己出题自己答**"。学生考试都给自己 100 分。

依赖检测**一开始就断了 AI 走捷径的可能**。

### 意义 3：提供降级路径

`[依赖检测]` 区分"必需 vs 可选"：
- **必需缺失 → 终止**（没法做的）
- **可选缺失 → 降级**（少一些功能但能做的）

**类比**：手术
- 必需：麻醉师、护士、手术刀（缺一不可）
- 可选：B 超机、心电图（缺了能做基础手术）

**降级路径让 Skill 适应不同环境**：
- 没 Design-Brief → 跳过 UI 一致性维度，其他照审
- 没 Playwright → 标 ⏭ 跳过交互验证，其他照审

### 意义 4：让 Skill 之间形成依赖网

`code-review` 的 frontmatter 里：
```yaml
depends_on:
  - product-spec-builder
```

**这是 Skill 系统的"零件契约"**：
- code-review 明确告诉系统："我吃 product-spec-builder 拉的屎"（粗俗但准确）
- 系统能据此组织流程：先 product-spec-builder → 再 dev-builder → 再 code-review

依赖检测 + frontmatter 的 `depends_on` = **Skill 链路衔接的基础**。

没有这个，每个 Skill 都是孤立的，只能用户手动协调。

### 类比：盖房子

**不依赖检测 = 直接开盖**：
- 没图纸？不管，开盖
- 没地基？不管，开盖
- 结果：盖一半发现不行，前功尽弃

**有依赖检测 = 前置齐了再开**：
- 图纸有了？✓
- 地基打了？✓
- 材料到了？✓
- 全齐 → 开工

**省的是"盖到一半发现不行"的浪费**。

## 问题 1：Spec 是否要改成具体的 md 文档名称？

### 先看现状

v2 里 "Spec" 出现的方式不一致：

| 位置                       | 写法                |
|----------------------------|---------------------|
| frontmatter 的 description | `Product-Spec.md`  |
| [依赖检测] 必需项 [1]      | `Product-Spec.md`  |
| [工作流程] 第一步          | `Product-Spec.md`  |
| [任务与边界] 做的第二条    | `Spec 每条功能`    |
| [第一性原则] 第 2、3 条    | `Spec 原文 / Spec 条目` |
| [审查维度] 功能完整性      | `Spec 每条功能`    |

**规律**：首次出现用全称 `Product-Spec.md`，后续用简称 `Spec`。

### 这样写对不对？

**对的，但不够严谨**。

技术文档的常规做法就是：
- **第一次出现用全称**（建立映射关系）
- **后续用简称**（避免啰嗦）

**类比**：
- 论文写「中国共产党中央委员会（以下简称"中共中央"）」，后面直接说"中共中央"
- 代码里写 `import { ProductSpec as Spec } from "..."`，后面用 Spec

### 改不改？给两个方案

**方案 A：保持现状，加一行声明**
在 [任务与边界] 开头或 [依赖检测] 开头加一句：
> 注：本 Skill 中提到的 "Spec" 均指 Product-Spec.md

- 成本：1 行
- 收益：消除歧义
- **推荐 ✓**

**方案 B：全部改为 Product-Spec.md**
- 优点：100% 明确
- 缺点：每句话都出现 `Product-Spec.md`，读起来累
- 不推荐 ✗

### 推荐方案 A 的理由

技术文档的可读性和精确性要平衡。
全称满地跑会让 AI 注意力分散到"读字"上，而不是"读规则"。

## 问题 2：括号里的内容是不是多余？✨（**你抓到 bug 了**）

### 原文

```
不做：
- 不修改代码（修复由主 Agent 路由 dev-builder/bug-fixer）
```

### 你的判断

> "我只说不修改代码不就行呢，后面是不是多余呢？"

### 答案：**完全正确，确实多余**。而且违反了我自己反复强调的原则。

---

### 为什么是 bug？

#### 第一处：[任务与边界]
```
不修改代码（修复由主 Agent 路由 dev-builder/bug-fixer）
```

#### 第二处：[初始化] 节末尾
```
注意：本 Skill 范围到输出报告为止。修复由主 Agent 拿到报告后路由：
- Stage 1 失败（功能缺失/不符合 Spec）→ dev-builder 补实现
- Stage 2 失败（代码质量/安全问题）→ bug-fixer 修复
- 修复完成后主 Agent 重新派发 code-review，从 Stage 1 开始
```

**两处都在定义"路由规则"**——这就是讲义里讲过的**重复定义** = **违反单一事实源**。

### 这违反的正是讲义里说过的话

回顾讲义的核心思想 #2：
> **单一事实源（Single Source of Truth）**
> - 同一条规则只能在一处定义
> - 有冲突时 AI 行为必定飘
> - 维护成本随冲突数量指数上升

我自己写的 v2 居然犯了——**这就是反面教材**。

### 后果

**短期没事**：两处定义现在还一致

**长期会出事**：
- 半年后改路由（比如新增一个 Skill `security-fixer` 接手安全问题）
- 你改了 [初始化] 末尾，忘了 [任务与边界] 的括号
- AI 行为开始飘
- 你查 bug 时，看到 [任务与边界] 写"dev-builder/bug-fixer"，但实际逻辑是按 [初始化] 走——**两边对不上**

### 改怎么改？

**[任务与边界] 节简化为**：
```
不做：
- 不修改代码           ← 删除括号
- 不自行决定修复优先级
- 不重构架构
- 不审查 Spec 之外的代码（除非命中 [Spec 漂移检测]）
```

**路由细节由 [初始化] 节末尾统一管理**。

### 推而广之：那"不自行决定修复优先级（按 [审查维度] 中明文 Priority 规则打标）"也有同样问题吗？

**有！同样的 bug。**

`Priority 规则` 在 [审查维度] 里已经定义了。
[任务与边界] 里再说"按 X 节规则打标"——
- 严格说不算"重复定义"，而是"指路"
- 但既然 [审查维度] 节里写明了规则，AI 自然会查到，**不需要这种指路**

**更彻底的简化**：
```
不做：
- 不修改代码
- 不决定修复优先级
- 不重构架构
- 不审查 Spec 之外的代码（除非命中 [Spec 漂移检测]）
```

## 修订版：v2.1 的 [任务与边界]

```
[任务与边界]
    > 注：本 Skill 中提到的 "Spec" 均指 Product-Spec.md

    做：
    - 对照 Spec 输出结构化审查报告
    - Spec 每条功能都要有对应结论（✅/⚠️/❌/❓ 之一）
    - 报告按 [输出格式] 节定义的统一模板呈现

    不做：
    - 不修改代码
    - 不决定修复优先级
    - 不重构架构
    - 不审查 Spec 之外的代码（除非命中 [Spec 漂移检测]）

    完成标准：
    - Spec 每条功能都被覆盖（无遗漏 = 不合格）
    - 每个 ⚠️/❌ 附 Spec 原文 + 代码证据（文件:行号）
    - Stage 2 安全扫描全量跑过
    - 报告按 [输出格式] 模板输出，含开头总览行
```

| 修复优先级 | `不自行决定修复优先级（按 [审查维度] 中明文 Priority 规则打标）` | `不决定修复优先级` |

## 反思总结：你揭示了什么？

| 你的问题                | 揭示的本质问题                              |
|-------------------------|--------------------------------------------|
| Spec 命名是否要具体     | 文档术语应统一：首次全称、后续简称、加声明 |
| 括号内容是否多余        | **写规则的人也会违反规则**——必须自查      |

### 元教训：写完 Skill 必须自查"五层体检"

我写完 v2 后**没自查就交出来了**。
你这次发现的 bug，正是"五层体检"第 2 层【**重复**】没过。

体检清单（再贴一次）：
```
1. 顺序：原则在前 3 节？核心在前 5 节？输出在后半段？
2. 重复：同一规则是否写多处？两处定义是否一致？  ← 你抓到的就是这层
3. 具体性：阈值有数字？判定有规则？
4. 例外：硬性规则有 buffer？
5. 可移植：跨语言？跨工具链？
```

**老师以后要自己先体检完再交作业**。
**学生现在已经会用体检图找老师的 bug 了** —— 你出师了。👍

## 进阶思考：还有没有别的"双处定义"？

我顺便扫了一下 v2，给你练手用：

| 嫌疑点 | 在哪 | 是否真的双处？ |
|---|---|---|
| `Stage 1` / `Stage 2` 的定义 | [审查维度] 顶部 + [工作流程] 第三步、第四步 | ⚠️ 一个是定义，一个是引用，**不算 bug，但可以让流程节直接说"执行 [审查维度] 的 Stage 1"** |
| `Priority` 颜色定义 | 各维度下分散 + [输出格式] 末尾 | ⚠️ 各维度的是"产出规则"，输出格式的是"汇总规则"——**职责不同，不算重复** |
| `失败话术` | [依赖检测] 一处 + [初始化] 引用 | ✅ 一处定义、一处引用，OK |

### 这就是健康的引用关系

- **定义只在一处**
- **其他地方引用而不复述**

v2.1 修订就是要消除"复述"，改为"引用"。
