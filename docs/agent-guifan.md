一、核心开发原则：让 Agent 专注且高效
编写 Agent 规范的 5 大核心原则，是避免模型 “罢工”、输出无效结果的关键，核心逻辑为先规划、再拆解、设护栏、持续迭代：
顶层愿景先行，让 AI 补细节
用简练的 “产品简报式” 概要规范启动项目，聚焦 “做什么、为什么”，将 “怎么做” 的细节交给 Agent；利用工具 “计划模式” 让 Agent 先做只读规划（分析代码、起草规范、提出疑问），定型后再执行编码，避免提前写代码的误区。
规范结构化，对标 PRD/SRS
把规范打造成有清晰章节的正式文档，而非零散笔记，且必须覆盖命令、测试、项目结构、代码风格、Git 工作流、边界六大核心领域，同时明确技术栈版本、使用统一格式（如 Markdown），让 Agent 易解析。
模块化拆解，拒绝单一大提示词
因模型存在 “指令魔咒”（指令过多会忽略部分要求），需将任务和规范拆分为模块化单元，每次仅给 Agent 当前任务的相关上下文；可通过规范摘要、子 Agent / 技能、并行 Agent提升效率，单 Agent 也可通过 “新会话刷新上下文、TODO 注释拆分任务” 实现模块化。
内置质量护栏，注入人类经验
规范不仅是任务清单，更是质量控制指南：设置始终执行、事先询问、绝不执行三级边界；让 Agent 自动自检（实现后对照规范核查），用 “LLM 裁判” 做主观评审（如代码风格）；将人类领域知识、避坑经验写入规范，同时根据任务复杂度调整规范细节（简单任务极简，复杂任务详尽）。
持续测试迭代，绑定工具链
将规范视为 “活文档”，在每个里程碑测试 Agent 输出，失败则更新规范并同步给 Agent；利用 RAG、MCP 等工具管理上下文，用 Git 做版本控制；根据场景选择模型（初稿用轻量模型，核心步骤用大模型），监控 Agent 动作并记录日志，持续优化规范编写技巧。
二、规范落地的关键工作流
四阶段闸口式工作流（GitHub Spec Kit）：确定规范（用户视角）→制定计划（技术视角）→分解任务（拆为可测试小模块）→实施（逐任务开发，分阶段验证），前一阶段未通过则不进入下一阶段，避免 “纸牌屋代码”。
Agent 协作模式：单 Agent 适合简单任务，多 Agent / 子 Agent 适合复杂项目（为各领域设专属 Agent，如数据库 Agent、API Agent），通过编排框架（LangGraph/OpenAI Swarm）和向量数据库协调，避免任务冲突。
规范的长期使用：将规范保存为文件（如 SPEC.md），作为跨会话的 “唯一事实来源”，解决 Agent “健忘” 问题；为多角色创建 agents.md，定义各 Agent 的行为和边界，让其各司其职。
三、Agent 开发的核心设计要点
关注 Agent 体验（AX）：用干净可解析的格式编写规范，为 API 提供 OpenAPI 模式，遵循 MCP 等标准化协议，让 Agent 易理解、可执行。
融合 PRD 与 SRS 思维：像 PRD 一样聚焦用户需求和 “为什么做”，像 SRS 一样明确技术细节和 “怎么做”，减少后期沟通误区。
人类的核心角色：开发者是 Agent 的 “管理者” 和最终质量过滤器，规范是协作的动态产物，若 Agent 输出偏离预期，可完善规范并重新开发，无需迁就模型。
四、必须避开的 6 大常见坑点
GitHub 研究显示，模糊是 Agent 规范失败的核心原因，需规避以下问题：
提示词模糊（如 “做个酷炫的东西”），需明确输入、输出和约束；
直接投喂冗长无摘要的上下文，未做模块化或 RAG 处理；
跳过人工评审，轻信 Agent 生成的 “通过测试的代码”；
将快速原型的 “氛围编程” 等同于生产级的 AI 辅助工程；
忽略 Agent 的 “致命三重威胁”：速度快、输出非确定、使用有成本，导致验证不足；
规范遗漏六大核心领域，缺失 Agent 必需的关键信息。
五、核心认知：AI Agent 是 “数字实习生”
与 Agent 协作的本质是管理数字实习生：需提供清晰的规范（指令）、必要的上下文，给出可操作的反馈；规范的价值不仅是引导 Agent 工作，更是让其自我纠错、守住安全边界，最终大幅提升 “一次做对” 的概率，减少无效迭代。
