# Product Spec 输出模板

本模板用于生成结构完整的 Product Spec 文档。
- 输入：用户的产品想法（通过 product-spec-builder 采访收集）
- 输出：Product-Spec.md（项目根目录）
- 下游：design-brief-builder / dev-planner / dev-builder 等所有后续 Skill 都会读这份文档
- 因此：内容必须完整、明确，不能有占位符或模糊描述

---

## 模板结构

**文件命名**：Product-Spec.md（放在项目根目录）

---

```markdown
# Product Spec — [产品名称]

**生成日期**：[YYYY-MM-DD]
**版本**：v1.0

---

## 产品概述

**一句话定义**：[这是什么产品]

**目标用户**：[具体描述：是谁 + 有什么特点 + 什么痛点]

**核心价值**：[用了这个产品能得到什么 / 解决什么问题]

**差异化定位**（如有现成竞品）：[相比现有方案，你的独特之处]

## 应用场景

**数量要求**：3-5 个具体场景
**多样性要求**：场景应覆盖不同用户类型或不同使用情境（不能 5 个都是同一个人）

- **[场景名]**：[具体的人] + [在什么情况下] + [怎么用] + [解决什么问题]
- ...

## 功能需求

**核心功能**（去掉就不成立的功能）
- **[功能名]**：[触发方式：点击 XX / 输入 YY] → [系统做什么] → [得到什么] [⚡ AI 增强]（如使用 AI）
- ...

**辅助功能**（有了更好但去掉不死的）
- **[功能名]**：[触发方式] → [系统做什么] → [得到什么] [⚡ AI 增强]（如使用 AI）
- ...

注：标 [⚡ AI 增强] 的功能必须在下方 [AI 能力需求] 章节列出对应能力。

## UI 布局（仅有 UI 产品填写，CLI / API / 库省略本节）

**填写边界**：
- ✅ 写：整体布局 / 区域内容 / 控件类型 / 主要交互
- ❌ 不写：颜色 hex / 字号 / 圆角 px 等精确数值（属 design-brief-builder + design-maker）
- ❌ 不写：视觉风格描述（"现代感"等）（属 design-brief-builder）

### 整体布局
[几栏、大致比例、固定元素等]

### 区域内容
- **区域名 1**：放什么
- **区域名 2**：放什么

### 控件规范
- **控件类型**：选项有 [...]，默认 [...]
- 不写精确尺寸 / 颜色 / 字号

## 用户使用流程

**路径数量**：1-3 条核心路径
**路径关系**：说明路径之间是【平行】/【顺序】/【可重复】

### 路径 1：[路径名]（如：首次使用）
1. [步骤]
2. [步骤]
...

### 路径 2：[路径名]（如：连续使用）
1. [步骤]
...

## AI 能力需求

**填写规则**：
- 应用位置必须对应 [功能需求] 章节中的某条功能（用功能名引用）
- 能力类型从下方枚举中选择

**能力类型枚举**：文本理解与生成 / 图像生成 / 图像理解 / 语音识别 / 语音生成 / 多模态 / 嵌入向量 / 工具调用 / 其他

| 能力类型 | 用途说明 | 应用位置（对应功能名）|
|---------|---------|---------|
| <从枚举选> | <做什么> | <对应功能名 + 触发时机> |

## 技术方向

**填写范围**：只写大方向。
具体版本号 + 详细包名由 dev-planner 经 WebSearch 验证后填写。

| 维度 | 选择 | 理由 |
|------|------|------|
| 产品类型 | Web / Desktop / CLI / Mobile / API / 库 | 为什么选这个平台 |
| 后端需求 | 无 / 简单（API route / serverless）/ 完整 / 仅后端 | 为什么 |
| 推荐技术栈方向 | 如 Next.js + TypeScript + Tailwind（不写版本号）| 为什么选这套 |
| 数据存储 | 无 / 本地（LocalStorage / SQLite）/ 云端 / 混合 | 基于产品需求 |
| 部署方式 | 静态托管 / 服务器 / Serverless / 桌面安装包 / App Store / npm 包 | 根据产品类型 |

## 技术说明（可选）

**填写时机**：仅以下情况需要写
- 涉及外部服务依赖：需要调用什么服务？有什么限制（QPS / 费用 / 可用性）？
- 涉及特殊要求：离线使用？系统权限？性能要求？

无以上情况 → 省略本节

## 补充说明（可选）

**填写时机**：列出产品的配置项、状态枚举、逻辑规则等需要明细化的内容

| 选项 | 可选值 | 说明 |
|------|--------|------|
| [选项名] | [枚举值列表] | [说明] |
```

## 写作要点

1. **产品概述**：
   - 必须明确写出**目标用户**：是谁 / 有什么特点 / 什么痛点
   - 核心价值：用了这个产品能得到什么
   - 不允许写"用户" 这种废话——必须具体

2. **应用场景**：
   - 具体的人 + 具体的情况 + 具体的用法 + 解决什么问题
   - 场景要有画面感，让人一看就懂
   - 5 个场景要有多样性（不同用户类型 / 不同情境）

3. **功能需求**：
   - 分「核心功能」和「辅助功能」
   - 每条格式：触发方式 → 系统做什么 → 得到什么
   - 标 [⚡ AI 增强] 的功能必须在 [AI 能力需求] 列出

4. **UI 布局**：
   - 仅有 UI 产品填写（CLI / API / 库省略）
   - 不写精确数值（颜色 / 字号 / 像素）
   - 控件要写主要交互，不写视觉细节

5. **用户流程**：1-3 条路径，明确路径关系（平行 / 顺序 / 可重复）

6. **AI 能力需求**：
   - 列出需要的 AI 能力类型（从枚举选）
   - 说明具体用途
   - **应用位置必须对应 [功能需求] 中的某条功能**（用功能名引用）

7. **技术方向**：
   - 只写大方向，不写具体版本号
   - 5 个维度 + 理由
   - 这是给 dev-planner 和 dev-builder 的输入

8. **技术说明**（可选）：仅在有外部依赖或特殊要求时写

9. **补充说明**（可选）：用表格列出配置项、状态枚举

10. **无占位符**：所有字段不允许 TBD / TODO / 待补充
    - 信息不够时让 product-spec-builder 继续追问
    - 不勉强生成半成品

11. **UI 布局边界**：颜色 / 字号 / 圆角 等精确数值不写
    - 属 design-brief-builder + design-maker 范围

12. **AI 应用位置必须对应功能**：
    - [AI 能力需求] 表的"应用位置"必须引用 [功能需求] 中的某条功能名
    - 不能孤立存在
